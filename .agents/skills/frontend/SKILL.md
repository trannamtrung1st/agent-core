# Frontend

Read [Frontend Implementation](../../../docs/13-frontend-implementation-spec.md); use [Protocol](../../../docs/14-api-and-realtime-protocol.md) and [realtime](../realtime/SKILL.md) for connection/audio changes.

- Use React/Vite, strict TypeScript, Zustand and Ant Design v6 directly in product components. Keep only minimal `app.css` for shell sizing, overflow, product layout, preview sizing and accessibility. Do not add generic AntD wrappers, Ant Design Pro/ProComponents/X, another UI framework, or a replacement custom design system. Services own connection/audio lifetimes; components subscribe, render and issue commands. Avoid SSR and Next.js.
- Visual presentation follows Ant Design defaults plus the short policy in [.agents/context/DESIGN.md](../../../.agents/context/DESIGN.md). [.agents/context/PRODUCT.md](../../../.agents/context/PRODUCT.md) is Impeccable tooling context only; `/docs` wins on product, architecture and behavior. For UI quality passes, load [impeccable](../impeccable/SKILL.md) and improve UX on the AntD baseline.
- Keep serializable UI/session projections in Zustand; PCM buffers, AudioContext and HubConnection stay in services. Guard deltas by attachment, response, event sequence and text offset; preserve tombstones until authoritative snapshot replacement.
- Render escaped plain text and interrupted/failed statuses. Retain drafts on reconnect, disable submission until ready, and provide labeled controls, keyboard access, visible focus and actionable errors.
- Register handlers before connecting and reattach on each new connection. On loss stop playback and discard input buffers; never replay microphone frames. Use same-origin URLs and documented Vite proxies; keep secrets backend-only.
- Follow one-session text/voice **mode** lifecycle. On Voice click, preflight microphone/AudioContext/worklets under user activation without sending PCM, then `session.mode.set(voice)`. While `pendingMode` is voice, render Starting voice… and offer Cancel. Start PCM only after the server applies voice. Release prepared resources on failure, cancel, timeout or disconnect. After reconnect the user must press Voice again. Mute affects input only; capture continues during output. Keep the labeled composer available while voice is live (synthetic Playwright sends text in voice). Do not hide it for a separate call layout unless [Frontend Implementation](../../../docs/13-frontend-implementation-spec.md) and those tests change together.
- Synthetic mode defaults to scripted hardware-free input/playback simulation, not recognition of arbitrary speech. Keep separate fake-device AudioWorklet coverage.
- Use [testing](../testing/SKILL.md#runtime-verification) for Vitest, React Testing Library, build and synthetic Playwright checks. For implementation, fixes and behavior reviews, use the configured Playwright MCP to exercise the affected user journey in the running Synthetic app when available. Perform the actual interactions and assert the resulting UI state; inspect console and failed network requests. Cover the normal path and a relevant error/recovery or boundary case when behavior changes. A screenshot, DOM snapshot or static review alone does not prove the feature works. If MCP is unavailable, run the applicable Playwright E2E scenario or another available browser tool and report the fallback and remaining gaps. Report device behavior that automated checks cannot establish.

## Component reuse and layout consistency

Apply this workflow when adding or changing UI, including spacing fixes. Plans identify reuse and verification scope without running the app; reviews inspect existing behavior and report findings unless fixes are also requested.

1. Inspect existing product components, `web/src/app/AppShell.tsx`, the affected feature layout, `web/src/app.css`, and [.agents/context/DESIGN.md](../../../.agents/context/DESIGN.md) before introducing markup or spacing. Find comparable headers, sections, control rows and content containers; identify their current consumers and the existing owner of each spacing rule. If equivalent layouts are duplicated, identify the smallest shared product composition that should own them.
2. Reuse or extend the existing product component/layout before copying its markup and styles. Compose Ant Design layout primitives such as `Layout`, `Flex`, `Space` and Grid directly where appropriate. When a repeated product structure needs shared behavior or spacing, extract a focused product layout component and use it at the affected call sites. Do not create generic AntD wrappers, a parallel layout toolkit, or speculative abstractions for one-off arrangements.
3. Give each spatial relationship one owner: the enclosing layout owns outer insets and section spacing; a row/stack owns sibling `gap` and alignment; a child owns its internal padding. Prefer parent `gap` over margins on each child. Check built-in AntD spacing and typography margins before adding overrides so nested containers do not double the intended inset or gap. Fix the owning layout instead of adding per-child offsets, negative margins or escalating specificity to compensate. **Additive inset:** padded shells (composer, Model overlay, outlined header Model chip) keep compact padding; nested text field/button/option keep Ant Design `paddingXS` (8px, `{spacing.controlInner}`, same as `.session-row-body`) via `theme.useToken()` so labels align and hover fill still has inner padding. Do not zero a text button’s padding or use negative margin to fake that alignment. Icon-only 32×32 hits stay padding 0. Follow [DESIGN.md](../../../.agents/context/DESIGN.md) **The Additive Inset Rule**.
4. Use Ant Design spacing tokens (`theme.useToken()`) and the existing spacing roles in DESIGN.md. Compact/default/section (8/12/16px) own shells and sibling `gap`; `paddingXS` owns text-control inner padding (session rows, Model chip, overlay options, composer field). Choose the same value for the same relationship across equivalent surfaces. Preserve deliberate differences between compact text controls and 32px icon hits. Avoid fresh pixel values at each call site. Keep any necessary app-specific layout rules shared and minimal in `app.css`; use explicit, limited variants for justified density or responsive differences rather than caller-specific patches.
5. Align equivalent content edges, labels and control groups through the shared container, flex/grid alignment and consistent widths. Make wrapping, shrinking and overflow intentional; prefer logical padding/margin properties for directional insets. Keep document/focus order, readable content and usable controls intact when rows wrap or content grows.
6. For implementation, fixes and runnable reviews, verify the affected layout and representative consumers of any shared component/style in the running app. Compare equivalent gaps, container insets, content edges and control alignment at wide and narrow widths and around an affected breakpoint. Include long/wrapped content and relevant empty, loading or error states. Use rendered inspection and computed styles or bounding boxes to diagnose discrepancies; screenshots alone do not replace the affected user-journey checks above. Report what was reused, where spacing is owned, the surfaces/viewports checked and any unverified cases. If runtime verification is unavailable, follow the testing fallback above and report the exact blocker; static inspection does not establish rendered consistency.
