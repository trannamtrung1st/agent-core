# Observability and Operations

## Canonical host shutdown and worker cutover

`SessionShutdownHostedService` stops the same canonical tenant runtime singleton used for execution/control. Its cached drain closes shared capacity admission, cancels supervised Runs and retires Voice and recipient output. Repeated stop/dispose does not start another drain. Cancellation of a stop caller's wait does not reopen capacity or abandon the underlying cleanup. Pending durable work retains its canonical recovery rules; shutdown is not permission to replay effects.

Only canonical tenant Run recovery, Automation/event admission and email watches execute on hosted passes. Old owner occurrence intake, Run dispatch, Experience reconciliation, event fanout and duplicate owner cleanup loops are removed. Existing diagnostic IDs, phase isolation, cadences and Synthetic/no-provider behavior remain. `AgentCore:MaxActiveSessions` now feeds the dedicated capacity owner. The browser removes only its obsolete owner-token local-storage key on startup; blocked storage cannot prevent app entry.

[Focused evidence](reports/runtime-registry-cutover-verification-2026-10-21.md) separates shutdown, native runtime/browser, store recovery and unrun production/physical-device/CI claims.

This qualification used disposable roots only and did not restart any user host.

## Tenant Browser persistent-profile reset operations

Open the actual Agent’s Connections page and use its independently authorized **Browser state** section for current profile facts and explicit named reset. Every request outcome requires deliberate **Reload Browser state** before another reset; a lost reply is never repeated automatically. The [UI qualification](reports/tenant-browser-profile-reset-ui-verification-2026-10-20.md) records local evidence.

Preflight reads bounded existing metadata without launching a Browser or creating a directory. Reset may close all of that Agent's persistent views and remove its saved Browser state; it retains the reusable exclusive `.lock` inode and never deletes sibling Agent/tenant profiles or ephemeral Sessions. No operator should infer deletion from a request acknowledgement, closed page or audit start. Only stored `reset` confirms verified absence; unknown/pending need deliberate factual readback and, if desired, a newly authorized reset.

Host loss cannot replay reset. The next independently authorized GET settles an abandoned pending operation from available same-operation native facts or records unknown; persistent use remains blocked until a new confirmed reset. Do not clear the Instance reset column, remove its audit IDs or bypass a live profile lock to recover. The existing automatic lifecycle sweep still retires native resources without deleting persistent bytes. Focused tests use disposable roots only; no development verification authorizes resetting a user's live profile. [Schema and rollback](15-persistence-and-configuration.md#tenant-browser-profile-reset-state), [evidence](reports/tenant-browser-profile-reset-verification-2026-10-20.md).

A timed-out Browser owner advances the retry cursor so later owners and file cleanup can proceed. Lifecycle mutations attempt reconciliation immediately after metadata commit. Busy/unconfirmed native closure remains pending and logs use normalized Browser cleanup reasons with resource identity, never URLs, page contents or profile paths. It does not launch a profile or delete its retained bytes. [Browser retirement evidence](reports/tenant-browser-retirement-verification-2026-10-20.md).

## Explicit identity bootstrap foundation

The multi-tenant cutover is in progress; the [delivery ledger](reports/multitenant-iam-delivery-2026-10-16.md) records remaining resource/Hub/UI integration. These commands initialize the new identity foundation only. Do not deploy intermediate source or reset an existing user database to make it start. No live-data deletion is authorized. The current schema guard refuses an incomplete/older populated baseline rather than migrating its unscoped records into a tenant.

For a **new, explicitly selected SQLite database and data roots**, set `Persistence:Provider=Sqlite`, its ConnectionString and attachment/workspace/artifact/definition-resource/credential-key roots through the existing configuration mechanism. Run the one-use command with five operator-supplied environment values: `AGENTCORE_BOOTSTRAP_LOGIN`, `AGENTCORE_BOOTSTRAP_DISPLAY_NAME`, `AGENTCORE_BOOTSTRAP_PASSWORD`, `AGENTCORE_BOOTSTRAP_TENANT_NAME`, `AGENTCORE_BOOTSTRAP_TENANT_SLUG`. No default credentials are shipped; missing values fail before identity creation. Database creation uses the tracked migrations. Bootstrap creates Account, explicit platform role assignment, initial Tenant and human Owner atomically, records audit, then exits without starting hosted workers or listening for traffic. The persistent singleton marker permanently disables repeat bootstrap.

In a private zsh terminal, a password can be supplied without entering it into shell history:

```zsh
read -rs 'AGENTCORE_BOOTSTRAP_PASSWORD?New account password: '
print
export AGENTCORE_BOOTSTRAP_PASSWORD
# Set the other non-secret AGENTCORE_BOOTSTRAP_* values and exact persistence roots first.
# Persistence__Provider and Persistence__ConnectionString must select the intended new database.
dotnet run --project src/AgentCore.Api -- bootstrap-identity
unset AGENTCORE_BOOTSTRAP_PASSWORD
```

Use at least 12 characters (maximum 256). Never pass a password as a command argument, commit it, print it or copy it into a report. After successful bootstrap, start normally with the same configured storage/key roots. SQLite startup fails clearly if identity has not been initialized; it never supplies an implicit local Owner or accepts an owner header in the new identity namespaces. Authentication cookies are session references validated against current server session, Account status and security stamp. Sign out revokes one device session; password rotation invalidates all previous device sessions. Keep Account cookie keys in `Persistence:CredentialProtectionKeyRoot/account-sessions`; they are purpose-separated from credential protection. Back up the database and private key/file roots together when preserving this deployment.

An intentionally ephemeral InMemory host instead requires explicit `Security:EphemeralBootstrap:Login`, `DisplayName`, `Password`, `TenantName` and `TenantSlug` configuration on each start. Supply its password through private environment/secret configuration (`Security__EphemeralBootstrap__Password`), never a committed default. `bootstrap-identity` refuses InMemory because its initialized state would disappear on command exit. Provider profile and store selection remain independent; Synthetic makes no provider requests.

Human authentication defaults to HTTPS with Secure/HttpOnly/SameSite Strict cookies. For native loopback-only development, explicitly set `Security:Http:AllowInsecureLocalHttp=true`; non-loopback cleartext requests still fail. Future cross-origin realtime entry points use exact configured `Security:Http:AllowedOrigins`; no wildcard or generic CORS authority is granted. The UI/API resource route cutover and launcher fixture updates must be completed before claiming the complete application startup journey.


## Three-layer context maintenance

This is an explicit offline one-way conversion. First drain/complete or deliberately cancel nonterminal old Runs using the previous application, then stop writers and back up workspace/resource/artifact/credential roots together. Do not restart or reset a user's active host as verification.

```bash
dotnet run --project src/AgentCore.Api --no-launch-profile -- migrate-context /absolute/path/agent-core.db /absolute/path/new-context-backup.db
```

The backup destination must be new and distinct. The command uses SQLite's backup API, preflights incompatible Runs, converts retained configuration transactionally, recomputes hashes with canonical application algorithms and validates before commit. A refusal rolls back conversion and preserves the backup/receipts. Normal startup fails with this command and drain/cancel guidance when conversion is needed; it never resets data or resumes retired checkpoints. Restore the previous application and complete data backup for rollback. Historical completed checkpoints remain audit-only.

Custom provider/model catalog routes must explicitly declare `DeveloperRoleSupport=true` only for a verified separate system/developer contract on the selected transport. Undeclared/unsupported routes are ineligible; `openrouter/free` cannot be selected for this hierarchy because its random routes do not provide a fixed verified contract. There is no downgrade or fallback. Run normal Synthetic checks without live keys. Live models need separate opt-in verification.

Context diagnostics contain only section IDs, source kinds/revisions, bounded field-source metadata, size/omission estimates and a fingerprint. Never log or export prompt bodies, learned/user content, results, arguments, keys or screenshots through this manifest. IDs belong in protected diagnostics, never high-cardinality metric labels. Token figures are UTF-8-based estimates.

## Latency model

Treat perceived voice latency as independent stages: speech detection + STT partial/final latency + Interaction Controller latency + LLM first-token latency + speech-segmentation delay + TTS first-audio latency + transport/buffering + browser playback. Streaming overlaps parts of this chain; the measured critical path, not a naive sum of overlapping spans, explains the user's wait. Capture each stage to find the bottleneck instead of reporting voice latency as one number.

## Latency instrumentation

Conversation latency is a product feature. Use Application ActivitySource `AgentCore.Runtime` and Meter `AgentCore.Runtime`, ASP.NET Core/HttpClient OpenTelemetry instrumentation, structured Microsoft.Extensions.Logging, and optional OTLP export. Capture server DateTimeOffset for correlation and TimeProvider monotonic timestamps for local durations. Browser uses performance.now() for durations and UTC timestamps only for approximate cross-device correlation. Never subtract unsynchronized browser/server wall clocks and report the result as precise network latency.

| Milestone/event | Capture location | Useful measurement |
| --- | --- | --- |
| speech detected | Browser VAD, plus server ingress receipt | Local speech→duck, ingress→candidate |
| first STT partial transcript | STT pump before mailbox admission | Speech boundary→partial (server observed) |
| final transcript | STT pump and mailbox processing | Final→model request / mailbox delay |
| interruption candidate / confirmed decision | Controller transition | Candidate→decision |
| model request start / first token | Adapter send and first normalized delta | Request→first token |
| first speakable segment | Application SpeechSegmenter release with responseId/segmentIndex | First buffered text→segment release; separate from provider latency |
| TTS start / first TTS audio | Adapter segment request / first PCM | Speakable text→first audio |
| audio sent | Binary output sender at actual send | First TTS audio→send; send→playback ack upper bound |
| client playback start | Worklet consumed first sample, reported ack | Local audio receipt→playback; server first-send→ack is an upper bound including RTT |
| cancel requested | Runtime after supersession mark | Decision→cancellation request |
| playback stopped | Worklet flush acknowledgement | Browser stop receipt→actual stop |
| response completed | Runtime terminal after delivery/save | End-to-end server-observed response lifetime |

Trace spans: session attach, user turn, brain decision, model generation, each TTS segment, interruption, persistence write. Long voice calls should not require one unbounded trace; link per-turn activities by correlation ID. Metrics: histograms for the durations above, mailbox wait, input/output queue depth, active sessions, discarded stale chunks, interruptions by decision, normalized failures, reconnect count and underruns. Pause counters `session.auto_paused` and `session.pause_reason` use only the canonical pause-reason enum (`manual|inactivity|silentEvaluation|initiative|disconnected|recovered|persistence|other`) as a `reason` tag. Speech counters `speech.partial.count` and `speech.playback.complete` have no content tags. Histograms `speech.final.latency`, `speech.segment.latency`, and `speech.playback.start.latency` are untagged milliseconds. Counter `speech.cancel.reason` uses only `reason=userStop|userBargeIn|newText|userSteer|disconnected|modeChange|ended|deactivated|other`. Counter `speech.error.code` uses a bounded error-code tag (no transcript, PCM, secrets, or vendor bodies). Counter `agent.progress.event` tags only `kind` (`preparing|readingAttachments|runningTool|waitingExternal|finalizing|other`) and `state` (`started|updated|completed|failed|other`). Histogram `agent.progress.active_ms` is milliseconds tagged only with `kind`. Progress instruments never tag message text, operation IDs, tool arguments, reasoning, or attachment content. Do not log native structured JSON, compatibility marker payloads, or speech text. User-text counters `user_text.behavior` and `user_text.queued` use only `behavior=queue|interrupt`. Histogram `user_text.pending_batch_size` records the clamped suffix length `1..8` with no labels when a pending batch starts; counter `user_text.pending_batch_started` has no tags. Response-stop counters `response.cancel.requested` and `response.cancel.stale` have no high-cardinality tags. Use provider alias, decision and error code as low-cardinality metric tags; sessionId/eventId/responseId belong in traces/logs, not metric labels.

Application code records those histograms on `ActivitySource`/`Meter` `AgentCore.Runtime`. Observed synthetic 20-turn numbers live in [Milestone 12 demo verification](reports/m12-demo-verification.md); they are measurements, not SLAs. Compose SQLite volume survival and the owner-capability path are covered by `scripts/compose-sqlite-volume.sh` (also run on Ubuntu in [GitHub Actions](../.github/workflows/synthetic.yml)) and [MVP handoff](reports/m12-mvp-handoff.md).

## Handled-operation failure diagnostics

Handled failures must remain diagnosable even when Core safely returns a tool error, retries cleanup, stays silent, or preserves an uncertain dispatch receipt. `HandledFailureLog` emits a Warning with `DiagnosticId`, safe `Operation` and `ErrorCode`, a real trace ID when present, and relevant Session/Response/Run/Instance or `CredentialId` identifiers. Credential IDs identify account records; account names, addresses and protected credentials are excluded. SMTP rejection adds the status enum as `FailureReason`. The compatibility Gmail adapter logs rejected/uncertain HTTP status and retains a safe exception snapshot for cancellation after dispatch.

`HandledFailureLog` and `DiagnosticLog` deliberately remain stateless static façades, consistent with ordinary logging helpers. Exception snapshotting and field formatting own no Session state, and no logger, service provider or mutable cache is stored globally. Production services/factories pass the existing singleton `IDiagnosticIdSource`; the established fallback is only for direct construction in isolated fixtures. This uses the existing dependency boundary and adds no logging service/interface or second logging pipeline.

The existing process-wide `RuntimeTelemetry` Meter/ActivitySource and local caches also remain static. They own operational observations rather than mutable conversation state. Local `SnapshotStats` retains only the newest 1,024 duration samples per named stage under a stage lock; its Count, P50, P95 and Max describe that recent window. Both ordinary and diagnostic recording share the same bounded path. The lifetime Meter still receives every measurement. The separately bounded timeline retains its existing configuration and content policy.

Warning enablement is checked once in the shared helper. When warnings are disabled or no logger exists, it returns no diagnostic ID, allocates no ID and does not traverse exception stacks. Trace failure status remains independent of log filtering. Callers propagate the nullable result through existing optional failure references; tool error JSON omits a missing reference. An explicitly supplied nonempty diagnostic ID is reused without consuming the generator.

The exception object on these records is a safe diagnostic snapshot: original exception types, HResult, stack frames, bounded inner causes, and HTTP/socket machine codes survive. Aggregate siblings are retained within limits of eight children per aggregate, eight nested levels and 32 snapshot nodes overall. Untrusted exception messages and `Data` are omitted because they may contain passwords, private URLs, provider bodies, DOM text or email content. No raw protocol logging is enabled. Safe user/tool errors remain separate from this server-only exception detail. IMAP search/read errors return the same diagnostic ID; the tool-step record includes that reference when present. Diagnosed model and TTS failures carry the exception-log ID into normalized failure events and conversation history; the category/code match the normalized provider failure. Model scopes retain the pinned safe provider alias. An adapter without an enabled warning logger leaves the ID unset so the runtime still logs its own failure reference.

Coverage includes account IMAP search/read, SMTP rejection and uncertain dispatch, account connection tests, durable email send fallback, public web fetch/HTTP transport and deadlines, model setup/stream/continuation failures, TTS transport, browser capture/interaction/launch/profile reset, sandbox wait/inspect/cleanup, voice startup, Skill/message admission, completion/initiative/compaction fallbacks, Session command dispatch and workspace cleanup supervision. Expected cancellation stays quiet except when dispatch may already have occurred and its outcome is uncertain. Validation/policy tool results still retain their safe reason codes; an exception is attached only when one exists.

`tool.step` uses Warning for error receipts, unsuccessful sandbox results, uncertain email sends and HTTP error responses; successful operations and ordinary pending/queued lifecycle states use Information. Inspecting an existing child Run failure is still a successful inspection. Explicit errors whose codes resemble lifecycle states (such as `Failed` or `ok`) use an `error.` prefix and remain Warning records. Failed steps never log arguments or result bodies. Each executing tool carries formatted log scopes for Tool, SessionId, ResponseId, CorrelationId, AgentInstanceId and AgentRunId. Console UTC timestamps and formatter scopes are enabled by default through `Logging:Console:FormatterOptions:IncludeScopes`; structured sinks can index those same fields. IDs remain excluded from metric tags.

For Compose investigation, `docker compose logs --since 30m` includes these warnings and their safe exception stacks. Filter by `Operation=email`, `mail_read_failed`, `smtp_rejected`, `dispatch_unconfirmed`, a Session/Run ID, or a copied `DiagnosticId`. Keep the exception lines following the matching record when collecting evidence. This adds no log-storage service or OTLP exporter; `Observability:OtlpEnabled` retains its documented limitation.

## Third-party HTTP error responses

`Observability:HttpErrorResponses:Enabled` defaults to `true` in appsettings and Infrastructure options. Set `Observability__HttpErrorResponses__Enabled=false` to disable shared error-body reads, parsing and warnings. Changes apply on process restart. Successful responses and redirects are untouched. Warning-disabled sinks also skip diagnostic reads.

The shared Infrastructure HTTP handler covers the named LLM, batch STT, TTS, Brave search, Gmail and Google OAuth clients. The public-web transport uses the same parser for already-bounded HTTP tool/fetch response bytes. Each failed HTTP response emits `Operation=http.upstream.error`, `DiagnosticId`, `TraceId`, `Integration`, `HttpStatus`, `ProviderCode`, `ProviderType`, `FailureReason` and `ParseState`; existing execution log scopes retain Run/Session correlation. The parser recognizes OpenAI-style errors, Google RPC/Gmail envelopes and OAuth string errors. It logs only allowlisted codes/types/reasons and fixed classifications derived from selected message phrases. Unknown provider values are omitted, never copied into logs. URLs, query strings, headers, raw bodies, free-form messages and provider details are excluded from these default warnings.

Inspection reads at most 16 KiB plus one overflow byte, with a one-second diagnostic deadline that counts toward the existing request deadline. Empty, malformed, deeply nested, oversized, timed-out or unreadable responses retain a safe parse state. Every consumed byte is replayed to the adapter; status, content headers, retry hints, normalized failures and retry policy remain adapter-owned. Caller cancellation is propagated and responses are disposed. HTTP tools retain their existing body limits; diagnostics add no unbounded reads. SMTP/IMAP, browser page content and in-band successful SSE error events retain their existing diagnostics.

The LLM reuses the handler’s bounded snapshot and read outcome rather than reading an inspected error stream again, including after diagnostic timeout. The existing LLM `LogProviderErrorMessages` local opt-in remains default-off: it can include redacted free-form text that echoes private user content. The shared switch also suppresses that legacy parser on registered clients when disabled. Direct manually constructed adapters outside the registered HTTP pipeline retain their explicit legacy setting.

## MVP optimization targets (not SLAs)

- Local speech detection→gain duck: <=50 ms on a reference desktop browser.
- Server receipt of speech evidence→interruption candidate: <=100 ms; browser speech detection→server candidate aim <=250 ms on local/demo networking, measured with clock uncertainty disclosed.
- Controller explicit-stop decision→stop command queued: <=25 ms.
- Browser receipt of stop→worklet stopped: <=50 ms.
- Browser receipt of first PCM→playback: approximately 60–120 ms with the default prebuffer.
- Final transcript→first model delta and speakable text→first TTS audio: record p50/p95 per provider/profile; initial demo aims below 1 second each, explicitly provider-dependent.

Collect a reproducible 20-turn demo run, report sample size, provider/profile, device, browser, network conditions and percentile values. Do not claim universal guarantees. Optimize queueing/cancellation before increasing model complexity.

| Instrument | Meaning | Bounded labels |
| --- | --- | --- |
| `automation_event_filter_evaluations` | Completed evaluations through durable filter recovery, including transient failures and exhaustion. Cached decisions and backoff polling do not add samples. | `source`: core/webhook; `outcome`: matched/filtered/retry_pending/retry_exhausted/permanent_error/other; `cause`: worker_budget/timeout/none/other. |

| `automation_event_filter_duration_ms` | Elapsed duration over the same admitted engine scope, including setup and disposal; count gives actual engine-attempt rate, including read-only filter previews. | None. |

Allocated bytes are reclaimable traffic, not retained bytes; the per-thread instrument excludes allocations performed by timer/background threads and is not whole-process memory.
