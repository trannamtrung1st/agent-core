## Timeouts and retry policy

Initial background Runs reserve up to 30 seconds (at most one quarter of the pinned duration), one final tool step and 4,096 output tokens for completion. Normal prose completion checkpoints `completionRequired` and offers only `work.complete` with no semantic response envelope or substantive tools. The model must summarize existing verified receipts in 1–2,000 characters and use NeedsAttention for incomplete work. Invalid completion arguments receive field-specific feedback and at most one corrected envelope within remaining time, tool-step, output and checkpoint bounds. The typed `CompletionCorrectionAttempted` checkpoint flag prevents the allowance from resetting after provider retry or restart. A second invalid envelope, or prose after that correction, fails as `completion-invalid`; an absent completion still fails as `completion-required`; a substantive tool during finalization fails closed. Timer/step/capacity cutoffs keep this completion tool available within the original hard deadline. Genuine provider failures retain the normal bounded same-Run retry policy below; a deadline remains `run-deadline`, and ordinary prose cannot manufacture success. A resumed completion phase restores its marker and receipts without reopening work.

Canonical scheduling clarification keeps the new current human input as intent. `TenantAutomationMutationRules.ConversationEvidence` supplies at most eight earlier nonstreaming turns from that same owning Session, bounded to 12,000 serialized characters and before the current source entries. Assistant prose is limited to received/heard text; the current input is excluded from historical evidence. Prior requests may resolve references but grant no authority. Independent admitted tasks receive no Chat history. Structural schedule validation still precedes semantic verification.

The generic Automation executor and `AutomationCommandPreparation` are retired. Canonical `TenantAutomationMutationService` observes the actual claimed Run and current owned target, applies the closed argument contract, uses the shared pure `TriggerScheduleCommands.NormalizeTenant`, and produces the exact prepared action/intent fingerprint. The normalizer receives Core-bound Session and reference time directly, with no local Profile owner or caller verification record. `ITriggerCommandAuthorizer` receives current human input or actual admitted-task intent, the typed operation, exact action and optional bounded untrusted conversation evidence.

Real verification resolves the operator catalog default through `ILanguageModelResolver` with purpose `TriggerAuthorization`, preserving declared transport/developer-role support and selecting its least supported recognized reasoning effort (otherwise its validated default). Synthetic uses an explicit typed decision fixture independent of text. The verifier starts with 512 output tokens and retries once at 1024 only on confirmed LengthLimit, within one shared 30-second deadline and caller cancellation. It discards all partial output and accepts only a completed stream with exactly one JSON decision. Deny, Ambiguous, malformed/oversized output, tools, filtering, incomplete streams and unrelated provider failures do not retry.

Semantic Allow grants no IAM permission. Current primary/secondary authority, source reads and required exact consent remain independent. Deny/Ambiguous produce no effect. Unavailable/invalid classification preserves the exact eligible action for qualified human Review through the canonical durable owner. Target, revision, policy or source changes invalidate preparation. No generic response-bound decision, local preparation receipt or repeated classifier call substitutes for current consent.

Interactive browser Runs reserve 60 seconds for requested cleanup before the final 30-second reply reserve. At 210 seconds of the unchanged 300-second active budget, Core cancels the substantive model call and checkpoints a cleanup phase. Only admitted Browser cleanup/verification capabilities remain available, including semantic observation, hover, dialog, click, existing-tab operations and close. Canonical protected commands retain their exact `run_browser_command` authorization branch; other consent operations, new tabs and download publication are excluded. Core rechecks the typed intent at Runtime admission and current preparation/dispatch targets. New substantive calls in a pending batch receive `finish_required/cleanup_reserve` without execution. Dialog decisions remain model-guided and must be justified by the user’s requested action. Core does not infer authentication from filling, clicking or closure. Cleanup recovery retains the same Run, response, durable receipts and generation fences.

Browser snapshot compaction also bounds older native observations nested inside completed exact-consent receipts. It preserves request/operation identity, approval and effect facts, untrusted-content marking and current source checks. Budget diagnostics recognize a matched completed approved Browser close receipt with native `closed`/`already_closed` status; missing, denied or uncertain observations establish no closure. Confirmed closure alone never establishes logout, including when a model reports a sign-in screen.

Interactive browser Runs reserve the final 30 seconds of their admission-pinned active execution budget (300 seconds by default) for a tool-free reply (maximum 2,048 output tokens). Core stops admitting another tool batch or another tool in a batch when the remaining budget cannot cover both its 30-second per-tool bound and the reply reserve. A work-phase model call is cancelled at the reserve boundary; the hard deadline and caller cancellation remain independent. Approval waiting pauses work, cleanup and hard-deadline clocks. Already committed receipts remain durable; unexecuted pending calls receive `finish_required` before the phase checkpoint, so crash recovery cannot replay them. A Core-only System checkpoint marker preserves the finalization phase and remaining budget. Standard and unattended admission budgets remain unchanged; initial background completion uses the reserves described above.

After successful recorded browser work, a provider timeout may start one bounded finalization phase within that remaining budget, with no browser/application tools, new effects or visible-prefix stitching. User stop/steer/disconnect never starts this recovery. Existing protocol repair stays bounded inside finalization; a requested tool fails closed as `finalizationToolCall`. Hard Run expiry is `Timeout/runDeadline`; provider deadlines retain setup/idle/total reasons; an unexpected provider cancellation is `providerCancelled`, and a per-tool timeout is `toolTimeout`. An explicit terminal `DeadlineExceeded` command may settle an expired but still-current claim only with exact revision/generation fencing; it cannot renew, retry, admit output/effects or settle a reclaimed/cancelled generation. Failed finalization preserves successful action receipts and the safe diagnostic. Closing a browser never establishes sign-out, and filling/clicking never establishes authenticated state.

Trusted prior-Run facts include only allowlisted failure code/reason, diagnostic identity, finalization reason, interruption and bounded registered tool outcomes. They omit failure-summary prose, arguments, page content, private URLs and protected values. Current and prior facts remain separate. The Chat reply outcome and recorded browser actions are presented independently, including when the reply fails.

SessionRuntime requires an `IAgentRunStore` adapter; the production factory binds that adapter to the canonical tenant stores and exposes only `CreateTenant`. It has required canonical continuation, attachment, artifact, Profile, Memory and Experience owners, without raw global Session/Profile dependencies or a generic creation entry. An admitted user Run paused before its first assistant entry resumes under the same Run and response while its claim remains valid; a superseding user turn cancels that unstarted Run. A durable terminal conversation save settles its Run even when its continuation callback is suppressed by pause or epoch changes.

Infrastructure disables automatic HTTP retries/hedging for generation POSTs. Session Runtime schedules a durable retry on the same AgentRun for Unavailable, RateLimited, or a Timeout classified as `setupTimeout` or `streamIdle`, only before visible output, without an uncertain in-flight effect, while attempts remain and cancellation has not been requested. The claim is released into WaitingToRetry; the coordinator claims the next attempt with the same Activation, Run and response identities and retained checkpoint/effect receipts. Safe RetryAfter determines a 1–300 second delay, defaulting to two seconds. Completed tool effects are not replayed. Authentication, invalid requests, caller cancellation and unsupported capabilities remain terminal. Total/unclassified provider timeouts and provider cancellation remain terminal except for the bounded tool-free interactive-browser finalization phase described above. A setup/idle timeout cannot prove that upstream billable work was not accepted; the bounded retry trades that possibility for recovery from transient stalls. Never stitch a retry onto visible partial text.

Separate default budgets: headers/connect 10 seconds, stream idle 60 seconds reset on any transport read (including SSE comment/heartbeat lines), total response 120 seconds per provider call. Guarded tenant model requests use explicit per-call deadlines; native `http-real` and Compose no longer select global inference settings. HttpClient.Timeout is infinite so explicit linked deadlines own cancellation. FailureReason distinguishes `setupTimeout` (no response headers received), `streamIdle`, and `totalTimeout`; the total deadline wins when it expires during setup. Caller cancellation remains Cancelled. Setup failure messages include the configured seconds without provider bodies or host paths. Existing logs, realtime errors, persisted failure references and UI diagnostic copy carry the bounded reason. Circuit breaker defaults: 50% transport/5xx failures, minimum 5 requests over 30 seconds, break 15 seconds. It rejects quickly as Unavailable; it does not replay requests. API keys and provider bodies are excluded from logs.

Map 401/403 Authentication, 429 RateLimited (safe RetryAfter), 400/422 InvalidRequest, 5xx/network disconnect Unavailable, local deadline Timeout, caller token Cancelled, requested unsupported feature UnsupportedCapability, others Unknown. Malformed or unusable assistant output after the request was accepted is `InvalidResponse`, not `InvalidRequest`. An Infrastructure `SemanticResponseLanguageModel` decorator around resolved language models normalizes the assistant response into `ModelSemanticResponseReady` and never logs raw JSON, function arguments, or marker payloads. When display and action are otherwise valid, omitted speech normalizes to `same` and malformed speech normalizes to `none` so the Chat answer is still delivered; `llm.speech.normalized` records `speechOmitted` or `speechMalformed` without the envelope. The strict schema and `agent_core_respond` require `disposition` and `action` (`chat.respond` or null) for general activations. Direct `UserTurn` requests carry `ModelResponseContract.RequireChatResponse`, tightening structured output and `agent_core_respond` to `Continue` or `Complete` with required `chat.respond` and non-empty `displayText`; runtime admission (`InvalidAgentStep`) remains the fail-closed guard if a provider ignores that schema. Voice turns ignore text on `same` and `none`. Omitted speech normalizes to `same`, and an unknown mode or empty `custom` text normalizes to `none` without failing the answer. The parser does not log response arguments. Application `AgentStepNormalizer` maps that provider-neutral envelope to one Agent Step. Omitted disposition and action, including the plain-text compatibility channel, become `Complete` and one `chat.respond`. An explicit null action stays empty. ## OpenAI realtime transcription adapter

The shipped `OpenAiSpeechRecognizer` live session is a no-op `DeferredSession`; `SpeechFactory` does not select Recognition Adapter=`OpenAI`. When implemented, `OpenAiSpeechRecognizer` opens an OpenAI Realtime **transcription** session (`session.type = transcription`). Recommended configuration:

```text
OpenAiSpeechRecognizer
    → OpenAI realtime transcription session
    → configurable realtime transcription model
    default recommendation: gpt-live-transcribe
```

The adapter opens a **backend** WebSocket to the current OpenAI Realtime transcription endpoint using the configured API key; the browser never receives that key. Unresolved provider commit contention makes one CAS-fenced fallback write of `sandbox_evaluation_settlement_conflict` / Inconclusive; if that also races, existing no-replay recovery retains ownership.

Finding publication merges only the native finding into the latest Attempt so concurrent Manual/native findings remain intact. Exhausted publication contention leaves the Attempt Pending/Inconclusive and the execution unpublished for the existing sweep's 30-second retry. Confirmed source revision/fingerprint change or lost authority uses technical Indeterminate/Inconclusive recovery fenced by the observed Attempt revision; a raced recovery write must reread and revalidate too. [Settlement contention verification](reports/native-evaluation-settlement-2026-10-27.md) records the focused follow-up.

## Session Goal implementation

The Domain aggregate and bounded plan rules live in `Domain/Goals`. `Application/Goals` composes transitions, authority, protected human access, model tools and bounded continuation. Both existing IAM stores implement the Goal port with their established lock/transaction owners. EF child rows contain checkpoint plans/states; the parent has no duplicate checkpoint projection. The [persistence owner](15-persistence-and-configuration.md#session-goal-persistence-and-cutover) specifies migration and retention.

Deliberate Work uses existing UserTurn admission with a frozen `GoalWorkContext` (Goal, checkpoint, accepted plan/hash, Goal revision, Session/Space, focus revision, checkpoint hash, input sequence and bounded task). Ordinary text/voice admission has no binding. Goal work keeps the incumbent provider, response, tool, cancellation and persistence paths. Approval continuations preserve the exact binding. Source references cannot rebind arbitrary historical Runs.

Automatic continuation is disabled by default. A human may allow 1–5 total successor Runs until an absolute deadline within 24 hours. Every observation and atomic admission rechecks current plan, focus, Space, lifecycle, Membership, original human and executor rights, model readiness, pending inputs, budget and safe conclusive predecessor state. One next Pending checkpoint follows the verified predecessor. Its Activation/ExecutionOrigin is GoalContinuation, numeric 11, with exact source/parent/root; ordinary retries use the Run owner. A queued bound Run is cancelled if intent/plan/focus/lifecycle changes before claim. Running work retains its original witness. The durable count never resets on pause, re-plan or restart.

Goal completion does not complete a Session. Session completion, end, deadline, archive or deletion never imply successful Goal completion. Protected Goal reads share the Session retention cutoff; physical deletion uses the existing retention owner. [Focused qualification](reports/session-goals-delivery-2026-10-27.md) records executed paths and external limits.

## Initiative 9 — Task delegation and communication

Task states are PendingDependencies, Queued, Running, Waiting, Blocked, Succeeded, Failed, Cancelled and NeedsAttention. Only persisted Run/dependency facts advance state. Readiness atomically creates one worker Session/Activation/Run; earlier-sibling dependencies admit no speculative worker. Current source claim, pinned/current tool capability, target opt-in, own IAM/model/Space and root bounds all gate admission. Exact repeats return saved receipts; changed request hashes conflict. Cancellation is a request; uncertain effects prohibit implicit replay. Deadline is absolute, bounded to 24 h; 2 child Tasks per source Run, 8 live descendants/root, 3 delegation edges. Completion is distinct from Goal verification.

See the [adopted proposal](proposals/initiative-9-task-delegation-communication.md), [removal audit](reports/initiative-9-source-audit-2026-10-27.md) and [local delivery evidence and limits](reports/initiative-9-local-verification-2026-10-27.md). The implementation has focused local verification; the report distinguishes exercised behavior from unrun deployment, provider and device qualification.

Task hint polling and Run dispatch use separately awaited cadence loops within the existing `AgentRunHostedService`. Slow hint collection cannot postpone the next Run pass. Both loops share host shutdown cancellation and are drained by the existing BackgroundService lifecycle; no new execution coordinator, queue or hosted service is added. Each hint collector takes the connection's dedicated poll guard, copies transport state under the delivery gate, reads stores outside that gate, reauthorizes, and reacquires the delivery gate only for current-attachment validation, sequence assignment and send. Denied coordination reads do not retire an otherwise valid Chat/voice attachment; any hint-cursor reset is restricted to the same captured subscription.
