## Implemented boundary

Canonical Run configuration resolves only executor-readable owned Sandbox profiles and effective saved Instance limits/scripts. It pins exact revision, observed source epochs, compatibility and server readiness. An older Run with an unverified setup cannot gain execution admission from later verification. These pins grant neither IAM authority nor SDK dispatch permission.

`ITenantSandboxRuntimeStore` reuses existing Session lease and execution tables. New reservations resolve actual tenant Session/Instance/executor/Run/profile ownership, active Session/Instance/executor, current exact claimed Run generation, Run/security revisions and independently scoped central IAM agent `sandbox.execute`, profile `sandbox.read` and private-source `credentials.use`. Lease reservation uses the exact admitted effective setup. Execution reservation atomically creates one Session/Run/tool-call receipt and advances the matching Ready generation to Executing with its active/last pointers. Duplicate same-hash requests never obtain another reservation; changed operation hashes conflict. A completed operation cannot reserve another generation for replay.

Factual CAS updates keep exact owner, generation, action, original timing/source and bounded streams. They cannot mint reset authority, attach a new active command, revive a retired generation or rewrite confirmed terminal output. Exact retirement facts remain writable after Run cancellation and logical Session deletion; no new generation or effect is admitted. InMemory shares actual backing and isolates retained process collections; its legacy exclusion uses immutable retained namespace ownership without taking Session locks under Sandbox locks.

Migration `20261017213309_TenantSandboxRuntimeOwnership` adds normalized tenant/executor/profile and Run/lease references to those existing rows. Actual ownership/profile revision/Run FKs, JSON scope checks and receipt revision CAS protect canonical records. Global rows retain their original null ownership/revision-zero meaning and exact JSON bytes; no tenant adoption occurs. Typed reservation checks bind the exact mutable generation; the historical receipt is not foreign-keyed to a changing current generation value. Final working-schema consolidation remains required.

Authenticated GET `/api/v2/tenants/{tenantId}/sessions/{sessionId}/sandbox` and exact `/executions/{executionId}` return bounded stored facts through `TenantSandboxRuntimeReadService`. Original Account/session/Principal and independent Session, agent and referenced profile read scopes are checked before and after storage I/O, with security and Session witnesses. The projection omits provider command/container identities, mount authority and source authorization. `storedState` and `liveAuthorityConfirmed=false` prevent stored facts from asserting current provider liveness or effect authority. No command/reset mutation endpoint is added.

## Exercised outcomes

- Publish an owned Sandbox-capable Definition, create its actual Instance and human Session, assign exact executor grants, verify the owned profile through a controlled offline adapter, submit text and claim the resulting actual Run. Its owner has no legacy Profile. Reserve a generation, save controlled Ready facts, reserve one command receipt and observe atomic lease pointers. Settle bounded output, reject stale CAS/hash/action/terminal overwrites, reopen SQLite and inspect the protected projection with provider sentinels absent. Expected and observed: one durable operation, retained exact facts and no global exposure/adoption.
- Revoke execution authority: captured security witnesses fail stale; refreshed witnesses still deny absent permission. Cancel the actual Run and logically delete its Session: current reads and new reservation deny, while exact command/generation retirement facts persist. Expected and observed: authority retirement cannot replay effects or prevent technical factual settlement.
- Change claim generation/Run revision, advance reservation time to claim expiry, change the admitted setup or exceed bounded deadline: reservation rejects and retains the prior generation without a partial receipt. Later successful verification changes only a future resolver result; old admission stays unverified and cannot be expanded by a caller.
- Give a human exact Session read, then agent Sandbox read, then profile read: only all independent scopes release stored facts. Revoke the profile grant: release denies. Logout/relogin or mutate unrelated security during storage I/O: captured read fails; an explicit current human/witness read recovers. Expected and observed: no retired or partially authorized projection.
- Retire a generation, then reserve it again for the same operation: reject before provisioning. An explicit distinct operation can reserve a fresh generation. Mutate the supplied or returned process list: retained facts stay unchanged in both stores.
- Create an actual Synthetic HTTP Session and read its empty Sandbox observation: 200/no-store, null environment and no live-authority assertion. Missing exact execution or a same-Account foreign tenant scope denies; anonymous and legacy capabilities return 401; POST command input returns 405.
- Issue direct invalid SQLite tenant/Run/profile/nullable-JSON updates: actual database constraints reject them and preserve the saved receipt. Migrate a disposable database with retained pre-migration global lease/receipt rows: exact JSON and values survive, no tenant root appears, and `foreign_key_check` is empty.

The Ready/completed/provider IDs in these fixtures are controlled factual inputs exercising persistence and protected inspection. They are not evidence that a tenant container, script, process or cleanup RPC ran. Existing tenant disposable verification and legacy SDK checks retain their separate evidence scopes.
