# Tenant OAuth store verification — 2026-10-17

Baseline: `6942ea25`. This review completes and verifies the durable OAuth attempt/grant persistence foundation that was unfinished in the working tree. It does not enable a tenant OAuth public flow. The full proposal remains active; canonical Application IAM orchestration, protected proof generation, provider exchange, consent/callback routes, scheduled expiry, runtime secret use and credential UI remain pending.

## Delivered boundary

- `ITenantCredentialOAuthStore` is implemented by the existing InMemory/SQLite IAM stores and registered against the same owning store and clock. Attempts bind an actual Credential and Tenant to the original human Account, authentication session and active User/Principal. Begin, claim and connection/disconnection commit recheck session expiry/revocation, current Account status/stamp and current tenant membership under the store lock/transaction.
- Pending attempts contain state/correlation digests and an opaque protected private proof supplied by the future orchestrator. The store does not generate or encrypt PKCE/nonce material. A claim atomically changes Pending to Claimed, clears the durable proof and returns it once. Competing claims have one winner; a crash after claim cannot replay the exchange. An attempt ID is not callback authentication.
- A five-minute maximum lifetime, one Pending/Claimed attempt per Credential, a cap of 128 unexpired active attempts per Tenant, explicit successor supersession and bounded expiry support lifecycle containment. Failure/denial/expiry/supersession clear private proof. Scheduling cleanup and choosing terminal-record retention remain later orchestration work.
- Connection accepts an exact server-derived grant transition: current active OAuth Credential, stable external subject/preselected address, closed purpose-specific scopes, unchanged ordinary configuration, logical/secret/AuthEpoch increments and matching Synthetic mode. It commits the protected value/profile, attempt outcome, tenant security revision and safe audit together. The port trusts verified provider facts from its Infrastructure caller; it does not itself validate a provider token or evaluate scoped permissions.
- Disconnect clears the local grant and advances all three Credential generations in the same security/audit transaction, superseding pending attempts. Remote revocation is not implemented here. Failed reconnect leaves the previous protected grant and Credential generations intact.
- Ordinary create/update/value writes cannot forge OAuth identity, scopes, connection state, payload or authorization generation. Ordinary metadata/status updates preserve the grant; a status change advances AuthEpoch. Public views/audit omit private proof, hashes, protected payload and secret generation.
- Profile rows derive Tenant from their actual Credential owner, with composite foreign keys. Canonical SQLite queries exclude null/foreign profile owners before inventory counts and paging. Per-Tenant/per-purpose external subject uniqueness permits the same Google account in separate Tenants and independent Gmail/Drive purposes. Legacy null-Tenant identities retain separate uniqueness and cannot consume owned records.
- Migration `20261016211213_TenantCredentialOAuthAttempts` and its snapshot cover these constraints. Composite attempt foreign keys bind both resource/member owners and the original session's Account; parent alternate keys support those references. No owner is inferred or backfilled. Every fresh SQLite fixture migrates and checks model parity. This remains an intermediate development graph requiring final consolidation, not an approved user-data upgrade/reset.

## Executed outcomes

The first runnable journey created a tenant Gmail/Drive Credential through its Application service, began an attempt, rejected a wrong browser proof, claimed once, atomically connected a locally protected fixture grant, read safe metadata, reopened SQLite, disabled without losing the grant, then disconnected. All four purpose/store combinations passed. No provider request was made.

The extended cases verified superseded in-flight work could not commit, denied reconnect and deterministic expiry retained the old grant, concurrent claims returned one proof, stale/replayed commits failed, and logout/password rotation/suspended membership prevented a prepared grant from saving. Rejected work left Credential/security revisions and success audit unchanged. Actual SQLite inserts rejected foreign Credential roots, foreign member/Account/session edges and duplicate active attempts. Profile-owner corruption failed closed through both canonical and legacy reads. Same-subject connections in separate Tenants/purposes succeeded, a duplicate within one Tenant/purpose failed, and an independent unowned legacy identity could coexist.

Two fixture issues were corrected during execution: using two wall-clock reads made a nominal five-minute lifetime slightly too long, and a registered second Account made an unfiltered platform Principal `Single()` ambiguous. The fixtures now capture one deadline origin and select the intended Account. The .NET compiler also caught an xUnit analyzer violation, corrected before execution.
