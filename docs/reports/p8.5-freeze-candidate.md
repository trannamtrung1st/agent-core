## Decisions implemented

`app.message.send` and `skills.load` continue the existing model/tool pump inside one accepted user-turn execution. The mailbox is the only writer. `SessionToolExecutor` does not apply either effect. Neither tool is an Agent Step action or a runtime progress event. `chat.respond` stays the terminal Chat action. `Continue` does not start another generation.

The model supplies trimmed `text` only, at most 2000 characters. Empty text and routing fields are rejected. Core binds the current session. The visible role is `applicationMessage`: completed entry text, no envelope, heard length 0, `speechText` null. Effect key `v1:{executionId}:{toolCallId}`. The same response text, or the same effect key, does not create a second visible entry. At most three admitted messages per execution. Prompt history, compaction, summary, completion, and initiative skip the role. A new admission publishes `session.entry.upsert` on the existing hub, with the same history-item fields as `session.ready`. A duplicate or cancelled send does not publish a second item. An already admitted message stays if a later send is cancelled. A steered turn drops a buffered send that has not been admitted, and that text is not spoken.

`skills.load` is offered on a tool-capable user turn when the pinned definition has a non-empty Skill list. The compact catalog omits procedure bodies. Keyword preload still pins at most three ids. A load on the same execution can raise the pin to four, with at most 8000 aggregate procedure characters, four ids per call, and two load calls (`SkillLoadCount`). Loading a Skill does not grant tools, credentials, or approval. Recovery reads the stored pin and skips keyword reselection when the assistant entry exists or `SkillLoadCount` is already positive. `app.message.send` is offered on a tool-capable user turn even when the Skill list is empty. A model without tools omits both capabilities and can still keyword-preload.

### Provider truncation and tool budgets

A Real turn that asked for a multi-file program could finish HTTP 200 with `finish_reason=length` and then be reported as `missingDisplayText` / "Malformed assistant envelope." Partial tool-call drafts were discarded. The conversational request default of 512 tokens, and a 12-step / 120-second tool loop, were too small for that work.

This correction does not move `1461567` or `ca3eb23`.

- `LengthLimit` before a parseable semantic envelope is `InvalidResponse` with `FailureReason=outputLimit` and the safe message "The model output was cut off before a complete response." A parsed malformed `agent_core_respond` payload keeps its precise reason, including `missingDisplayText`.
- `finish_reason=length` with one or more partial tool drafts is `FailureReason=toolCallTruncated` on channel `toolCall`. The draft is not executed and its arguments are not copied into the safe message, log line, or history failure reference.
- A tool-offered conversational request sends `max_tokens` 8192. Definition `maxOutputTokens` stays 1..4096. Compact evaluators keep their own smaller requests.
- Interactive tool execution allows 24 steps, 30 seconds per tool, and 180 seconds overall. Per-tool timeout, cancellation, steer, approval, and output-byte bounds stay in place. Reaching the step cap fails as `InvalidRequest` with "Tool step limit reached." and a diagnostic id.
- Error details may show allowlisted Reason and Channel when the failure reference has them.
