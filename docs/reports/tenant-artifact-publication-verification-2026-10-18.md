## Implemented behavior

An original human-message Run may use its already granted `artifacts.create` capability to publish one immutable UTF-8 file. Core supplies Session, Run, claim and Artifact/operation identity. The actual parent Session is an explicit creation scope for `artifacts.create`; the Agent needs independent raw `sessions.read`. Agent creation permission and the requester's permission remain separate: current requester-aware or Always policy can require Review even when the Agent has permission. Missing delegatable authority may require an exceptional grant. Both cases return a decision without creating a file, receipt or approval request; prepared publication consent is not yet converted.

`TenantArtifactToolContract` rejects duplicate/unknown fields, caller-selected ownership/IDs, invalid MIME, excess arguments and content. It preserves exact content and line endings, normalizes safe metadata and hashes a tool-specific canonical argument form. Bounds are 32 KiB UTF-8 content and 64 KiB JSON arguments. Canonical JSON preserves Unicode without expanding an otherwise valid bounded payload beyond its argument limit. Tool offering requires an eligible human-message execution, actual Session context and the explicit existing Definition capability. Autonomous and continuation publication remain closed. Existing immutable publications receive no implicit new tool grant.

`TenantArtifactOperationService` uses the existing direct local effect/Run receipt owner. Common receipt lookup and live-Run/exact-source checks now live with the shared local receipt rules, while preference and Artifact writes keep family-specific ports. The owning adapters repeat actual source, current executor/requester Account state, capability, raw permissions, review policy, expected revisions, live generation/lease and cancellation checks. InMemory publishes the copied bytes/metadata with the Run marker, receipt, security revision and effect audit under existing ownership locks. SQLite stages a derived private blob, then commits metadata, Run marker, receipt, security revision and audit in one database transaction. No new schema, receipt table, grant ledger or execution engine is introduced. Instance configuration revisions remain unchanged.

An identical trusted Run/call returns the saved receipt; changed arguments conflict. The Runtime leaves the local marker to this atomic owner instead of placing an external InFlight marker before dispatch. That mismatch was reproduced during initial model execution and corrected. Model output is only `{ decision, reasonCode, applied, operationId }`; it conveys no file bytes, metadata projection, read grant or rich-reference authorization. Human download remains independently scoped through the existing canonical API. Effect audit records no file content. Failed staging/metadata transactions can leave unreachable private files for future scoped cleanup; no visible Artifact or receipt is inferred from such a file.

The existing definition baseline reader is shared by converted protected operations, and the renamed common direct receipt lookup still uses the same receipt collection/table. SQLite test composition now pairs its late-replaced database services with the actual SQLite Artifact adapter and root, rather than retaining a mismatched memory adapter.

## Observed workflows

Both actual store integrations bootstrap a tenant, create an existing Customer Support v3 Agent, create/admit a human Session/Run, claim that Run and grant creation plus independent Session read on its exact parent Session. Publication creates one owned file and matching receipt/Run marker without an Instance configuration mutation. Reading the file through the current human service yields exact Unicode/line-ending content. Identical replay produces no second row/audit; changed content conflicts. SQLite store recreation returns the original receipt.

Both-store HTTP/model cases use the actual offline language-model adapter, worker, Runtime and tool dispatcher, rather than directly invoking publication from fixture setup. A scripted model proposes bounded inline content; current Allowed authority produces one file whose ID matches the receipt and whose exact bytes download through the authenticated tenant API. Always Review and missing Agent permission produce `requiresApproval`, no file and no receipt. Agent `artifacts.read` remains absent. Every hosted case records zero outbound provider HTTP. These are backend integration/HTTP workflows, not browser UI or live-model acceptance.

A requester lacking creation authority independently triggers Review while the Agent has exact scoped creation permission. Granting that requester the same Session-scoped creation permission permits the normal Allowed path; the Agent's roles are never merged with the requester's roles. No approval request is fabricated. Direct store calls also reject missing independent Session read.

Commit gates race role revocation, policy tightening, lease expiry, request cancellation, Run cancellation and a competing identical caller in both stores. Loss/expiry/cancellation yields no published row, receipt or effect audit; competing calls share one winner. A SQLite save interceptor fails the receipt save after private staging: Artifact metadata, Run revision, receipt, security revision and effect audit all roll back. A subsequent explicit retry publishes exactly one visible file. Existing quota, human read fencing, legacy exclusion, migration/reopen, tamper and symlink tests remain green.
