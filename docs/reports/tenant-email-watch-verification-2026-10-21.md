## Implemented source and execution ownership

The existing EmailWatches/EmailWatchEvents, Core receipt/delivery/bucket, Automation occurrence/consent, Session and Run owners are reused. An enabled tenant-owned account watch is the polling source; it retains neither the configuring human's reusable authority nor a fabricated Agent actor. Polling rechecks the exact claim, active owned account and logical authorization fingerprint around provider work. Protected OAuth token refresh changes secret revision without changing logical source authority.

Baselines skip historical mail. A successful bounded scan atomically commits its cursor, pause release, metadata-only facts, complete receipt-time subscriptions and hidden actual binding/lease/account proofs. Account headers, bodies and tokens never enter event metadata. Current bound active executors need independent credential read/use, email read, Core read and Core trigger policy; a subscription creates no grant. Source failures use closed safe codes; the worker is bounded to three accounts, 60-second scans, 90-second leases, 25 references/page and 1024 receipt/child-delivery targets per cursor commit. Excess fanout refuses the entire batch.

Watch-off, pause, account changes, unbinding and lifecycle changes fence unadmitted input. Initial coalesced admission independently selects the currently eligible ordered email subset in the Application and both owning stores. Original bucket membership remains factual; prepared consent cannot retarget its retained subset. Account read/use Review joins the exact compound admission. Missing raw read/use is never supplied by a creation exception. Already admitted work survives ordinary watch-off while retaining original account/binding/raw-read/Review checks, including the owning NoAction completion boundary.

Core facts, Event Activity and approval visibility apply original account scopes and actual resource existence before counts/pagination. Retained coalesced rows expose only their included batch; excluded rows have a factual skipped result with no batch/work link. The shared approval scope helper now treats source-primary permissions as exact resource checks instead of demanding tenant-wide source access.

The frozen SQLite migration installs 75 guards, preserves incumbent/legacy data and guards, checks literal source evidence, and uses a deferred reciprocal Core-to-hidden-proof FK so no unproved email source can commit. Canonical proof/source facts remain immutable. Unbound credential deletion retires the actual owner first inside the outer security/audit transaction, allowing its watch/secret cascade while retaining factual receipts. Deleted originals disappear before human counts and fail execution source checks. Interim legacy filters are fail-closed coexistence, not completion of the proposal's final schema/authority removal.

## Observed scenarios and corrections

- Both stores: configure an actual connected tenant account; baseline a pre-existing Synthetic message without a receipt; add a new message; retain exactly four lookup fields with the actual tenant/Instance/executor; reserve the required account Review with no work; approve once and admit one owned Run. Watch-off before matching and while pending consent denies admission; accepted work retains its source after ordinary watch-off.
- Mixed accounts: coalesce input from the first account, turn that watch off, bind and baseline a second account, then receive its new message in the original window. The original two-source bucket remains intact; consent and runtime freeze only the second source. Activity shows the excluded first input as skipped with no batch/work reference, and the retained input with batch count one.
- Authority/lifecycle: scoped readers see zero Core/Activity/approval counts before original-account permissions and exactly one afterward; an exact account grant opens the source Review detail. Source-use revocation blocks matching and an already claimed NoAction completion. Unbinding then deleting the original account succeeds, retains factual proofs, and hides original-dependent facts/approvals even from a tenant-wide owner.
- Leases/recovery: concurrent claims coalesce, expired claims cannot advance the cursor, a substituted claim cursor is refused and a completed claim cannot commit twice. Paused recovery remains fenced until a successful scan. Protected-token-only refresh preserves logical account revision and a valid claim. SQLite application recreation preserves pending exact consent or admitted work with the same identities and current source fence.
- SQLite negative writes: hidden proof updates/deletes and owner stripping are rejected. A closed actual Core email source can be staged inside an outer transaction, but committing without its reciprocal hidden proof fails and rollback leaves no fact. Unknown watch fields are refused. Legacy-only migration roundtrip retains prior facts and guards without pending model changes or FK violations.
