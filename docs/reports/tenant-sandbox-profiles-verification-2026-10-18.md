## Implemented boundary

`/api/v2/tenants/{tenantId}/sandbox-profiles` supplies authenticated cookie/CSRF collection GET/POST and exact current/historical GET/PUT. Stable server-generated profile IDs have exact `sandbox-profile` scopes. Existing `sandbox.read/manage` support those scopes; `sandbox.execute` remains agent-scoped. The permission catalog reports supported `resourceTypes` alongside its primary type. Exact grants cannot create siblings or confer execution authority. Readable metadata is filtered before search/count/paging; the SQLite query filters/counts/pages normalized metadata before loading profile JSON, with the same literal invariant-uppercase behavior as InMemory.

`TenantSandboxProfileService` resolves the actual original Account/session/tenant Principal and repeats human/security/current-permission checks after protected I/O. Save appends an immutable profile revision with expected profile/security witnesses. The specialized actual InMemory/SQLite IAM adapters commit profile ownership/row, security CAS and audit together, with another original-session check inside the transaction. Rejected attempts leave profile/history/security/allowed audit unchanged. Owned rows cannot be listed, read, overwritten or verified through global Sandbox store methods, including an attempted write whose JSON omits tenant ownership. Global writes check ownership and revision in the same transaction.

Image preparation reuses the existing bounded tag/short-name resolver and host source/limit policy. Private sources require separate exact Credential read/bind/use and actual current tenant ownership, purpose/status/repository scope and revision/secret epoch. `SandboxImageAuthorization` carries trusted original-human/security evidence; a tenant ID on a profile is insufficient to release protected registry authorization. The Infrastructure adapter rechecks that proof after credential lookup and before protected dispatch; its global overload and unframed auth helper reject tenant profiles. Protected values/SDK auth remain inside Infrastructure. Safe API projections omit credential epochs and cannot assert saved verification or admission. A disabled unchanged source can retain old references after credential rotation/deletion so safe disabling remains available.

Migration `20261017200405_TenantSandboxProfileOwnership` adds an actual tenant root/FK, UTC-millisecond creation time, indexed owned profile rows and normalized search metadata over the existing append-only table. A composite ownership FK and strict JSON tenant CHECK reject foreign or missing/null ownership on an owned row. Prior global rows are not imported or adopted. This is the working schema's forward ownership step; the final clean canonical baseline and obsolete global-model removal remain required. Only disposable test databases were migrated.

### Executed use cases and observations

- Through real Synthetic HTTP, sign in, create a pinned profile, inspect current and historical revisions, search/page, reject an incorrect revision and explicitly save a disabled successor. Old history remains immutable and the new revision is Disabled. No-store, invalid limits and strict unexpected tenant attribution are verified. Anonymous and owner-token-only canonical calls fail; a second tenant of the same Account sees no profile or count, and global catalog/detail omit the owned ID.
- Register a minimal member and assign an exact profile role through the actual role-assignment HTTP route. Only its selected profile is visible; creation is denied, exact update succeeds, and revocation denies inspection/update before stale or invalid revision reporting. Catalog metadata exposes `sandbox-profile` only for read/manage, never execute. Both store adapters also reject sibling reads and filter hidden names before search/count/paging, including Unicode `résumé_100%` literal matching.
- Prepare two same-witness saves on separate tasks. Exactly one revision/security/audit commit succeeds; explicit history and reopened SQLite retain that result. Actual relational FK and JSON CHECK failures prevent cross-tenant or missing JSON ownership. Global reads, writes and verification cannot recover an owned source, even when a global write strips its tenant field.
- Intercept an actual owned profile read, sign out its original authentication session and create a replacement login before releasing the captured result. The old read is denied. Intercept immediately before the actual specialized write transaction, retire the original login and sign in again: no profile, security or allowed audit change occurs. An explicit attempt with a fresh session succeeds once.
- Use an actual tenant-owned protected Container Registry Credential. Profile management with Credential read/bind but no use is denied; adding exact use enables the selected save. A foreign tenant cannot borrow that credential. Rotation invalidates the old epoch at atomic commit with no partial update. After credential deletion, source inspection becomes unavailable while explicitly disabling the unchanged profile still succeeds. Protected sentinels are absent from audit.
- Resolve an actual tagged image against an isolated loopback registry with the expected dummy protected authorization. The saved reference is the returned immutable digest. On a second preparation, revoke the original human after the protected credential lookup, before auth release: **zero additional registry requests**, unchanged saved revision/security. A replacement login cannot complete the retired attempt; explicit fresh-session recovery sends the next request and saves one successor. No global/unframed source helper can bypass this proof.

## Review corrections and limits

Initial compilation identified an ambiguous SDK/Domain Credential type and a missing port import; both were corrected. Review found that a tenant marker alone must not authorize registry secret use; the trusted proof/recheck boundary and actual loopback revocation case were added. The shared API regression initially found a status-code change from 400 to 403 in the incumbent global invalid-source path; source handling was separated correctly and all 18 API cases pass. Review also tightened original-permission-before-revision ordering, strict JSON ownership NULL behavior, normalized database paging and actual separate-task CAS verification. Initial migration drafts were regenerated before any user database use; only the final migration is retained. The existing EF CLI/runtime version advice was non-failing and tooling was not upgraded.

Backend behavior was exercised through WebApplicationFactory, actual services/stores, disposable SQLite/reopen and a real loopback registry. There is no frontend source or presentation change in this checkpoint, so no browser/Impeccable acceptance is claimed. The catalog deliberately reports NeedsVerification/Disabled and never treats a global verification observation as tenant execution authority. Tenant verification, Instance selectors/settings, runtime permissions/effects, cleanup and the UI must use their own canonical boundaries before exposure. Production multi-tenant Sandbox isolation remains unverified and unaccepted.
