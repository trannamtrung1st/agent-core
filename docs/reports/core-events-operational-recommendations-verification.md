## Implemented and exercised

- `scripts/event-storage-snapshot.py` opens an existing SQLite database read-only/query-only with one read transaction. It reports aggregate retained row counts, UTF-8 JSON bytes, source/reviewed/unreviewed reference counts, pending buckets, allocated/free pages and main/WAL/SHM file sizes. It emits no event payloads/IDs/credentials and performs no application writes, pruning, vacuum or checkpoint. Missing files/schema fail instead of creating a database or reporting zero history. A WAL fixture preserves exact evidence, excludes uncommitted rows and observes committed growth from one to two webhook receipts. The command also runs successfully against the migrated task-owned `/tmp/core-operational-native/app.db`: 64 Core receipts, 64 external receipts and 64 external deliveries; respective JSON totals 46,777 / 7,798 / 41,408 bytes. No buckets exist in that fixture. `/tmp/core-recommend-storage-snapshot.json` records the aggregate sample. Whole-database page/file sizes include unrelated tables and WAL; they are not event-only footprint estimates.
- Untagged `automation_event_filter_allocated_bytes` and `automation_event_filter_duration_ms` histograms measure admitted nonempty engine scopes, including setup, errors and disposal. Pre-admission validation/worker rejection is excluded. The synchronous thread allocation sample is not whole-process or retained memory. A sustained real evaluator test observes exactly 1,032 paired samples (1,024 matching predicates plus eight Jint exceptions), positive allocations and finite durations without identity/payload labels. Blank/grammar-rejected evaluations add no samples. Existing recovery counters supply bounded source/outcome rates. [Operations](../17-observability-and-operations.md#observing-event-recovery-pressure) documents collection with runtime GC counters and low-frequency history growth snapshots; no production traffic baseline, alert threshold or recurring monitor is fabricated.
- An internal, per-evaluator options hook allows deterministic tests of Jint 4.4.1's actual constraints while production DI keeps the public parameterless constructor and original limits. The test expires the real TimeConstraint's timer synchronously after Jint resets constraints, verifies its `Check()` throws `TimeoutException`, and observes `filter-timeout` through the real evaluator eight times. A separate case cancels the caller at the same execution boundary and observes `OperationCanceledException`. Test-only CLR identity tracking populates the exact wrapper cache cleared by `Engine.Dispose`; every captured cache loses its wrapped object after unwinding, and a fresh evaluation still matches. This is actual Jint constraint execution, without wall-clock sleeps or unrestricted JavaScript. It proves timer-expiry handling, disposal and worker release; it does not model a CPU-heavy JavaScript expression naturally overrunning 100 ms. The earlier injected-timeout-only evidence limitation is superseded for this deterministic constraint path.
- Existing 12,000 measured memory evaluations across matched, filtered, non-Boolean and exception paths still pass. Allocations are approximately 23.9–28.3 KB/evaluation; the largest positive post-GC growth in this run is 499,864 bytes, below the broad 8 MiB ceiling. This remains a bounded regression check, not a leak-free production guarantee.

The [retention contract](../15-persistence-and-configuration.md#core-event-outbox-and-filter-snapshots) explicitly retains Instance-lifetime history. The review recommends eventual compaction as a separate deliberate policy; this follow-up records the requirements for audit horizon, pending retry/unreviewed evidence preservation, owner scope and durable dedupe/tombstones. It does not silently choose a deletion age or remove reviewed/flushed history. InMemory monitoring uses comparable runtime heap/process trends and Instance counts; the SQLite script does not claim exact InMemory row counts.
