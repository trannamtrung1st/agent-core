## Finding and correction

`TenantRunExecutionAuthority.CurrentDefinitionAsync` returned the admitted Run Definition after validating current ownership/requester/claim. That preserved immutable payload but made later publication or sparse Instance restrictions invisible to callers asking for current capability/isolation policy. It now calls the shared current-policy-only resolver between fresh exact claimed Run/requester/security checks. Current lookup reads actual owned or immutable shipped publication and sparse settings/self-management. It does not refresh resources, credential bindings, image eligibility or any admitted payload.

The existing Runtime current Definition checks now see later policy restrictions. Run context, instructions, persona, capability selection and setup remain separately pinned; newly available capabilities are not added to that admission. Callers requiring isolation must restrict admitted/current policy. The actual Synthetic Runtime scenario below verifies that adopting new policy does not rewrite model instructions for a previously admitted Run.

Sandbox metadata reservations previously checked active owner, claim, security/Run witnesses, raw scoped IAM and admitted setup, but not the actual current publication/Instance setup. Both store adapters now resolve current publication and Instance policy inside their existing transaction/gates. The shared rule rejects removed execution capability or allowed profile, admitted resources above current CPU/memory/pid/command/storage/idle/lifetime ceilings, changed Instance initialization script and a recorded home mount incompatible with the restriction of admitted/current isolation. Refreshing a security witness alone cannot bypass those restrictions. Compatible recovery can permit the original saved admission again; current relaxation cannot widen its admitted mount. Exact factual settlement remains separate and available after authority retirement.

No new schema, persistence resource, scheduler, host process, public HTTP endpoint or execution engine was added. These reservations still do not dispatch an SDK command or consume the mandatory Sensitive Sandbox review. `sandbox.execute` remains nondelegatable and classified Sensitive by the central catalog; raw IAM Allows must never bypass its required exact review when command dispatch is integrated.

## Exercised outcomes

- Publish an owned Sandbox-capable Definition, create its Instance and Session, admit and claim an actual Run. Publish/adopt a second version removing Sandbox capability or its allowed profile and disabling home. Current authority returns the adopted policy, while retained Run version/instructions/capabilities stay unchanged. With refreshed security witnesses, old Sandbox generation reservation denies with `sandbox_policy_changed`. Expected and observed: current restriction applies without rewriting admission.
- During current built-in source lookup, change tenant security or request Run cancellation. Captured policy returns null in both stores. A fresh read recovers after the unrelated security change, while the cancelled Run stays denied. Expected and observed: captured source cannot survive a changed security/claim authority boundary.
- In memory and SQLite, reserve a controlled Ready generation. Tighten current CPU or home access and refresh the security witness. Execution reservation denies with `sandbox_setup_changed` or `sandbox_mount_policy_changed`, creating no receipt and preserving lease revision. Explicitly restore compatible settings: the original bounded admission may reserve one receipt. Expected and observed: a new witness is insufficient to bypass current policy, and recovery uses the original admission.
- Admit a Run under a Definition with home Disabled, then publish/adopt a version allowing ReadWrite. A broad mount reservation still denies; a Disabled mount matching the original admission is accepted. The relaxation test uses supported publication adoption, since Instance settings can only narrow their Definition's home ceiling.
- Through actual authenticated HTTP, create an owned Definition/Instance/Session and admit text. Claim its Run, publish/adopt changed instructions/capabilities/home policy, inspect current authority and dispatch through the production tenant Runtime host. Expected and observed: current restriction is visible, the Run completes with text, all captured model AgentInstructions sections contain the original marker and exclude the new marker, and the Run has no legacy Profile.

Ready generations and mount identities in the store fixtures are controlled metadata facts. No tenant container, mount, process, script or SDK cleanup was exercised. The HTTP/Runtime case exercises text and policy/payload separation, not a newly enabled Sandbox command. Existing supported preference, approval, requester and dispatch regressions cover the shared authority consumers separately.
