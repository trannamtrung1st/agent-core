# Tenant OAuth backend flow verification — 2026-10-17

Baseline: `64c6f6e8`. This successor wires the previously verified attempt/grant persistence into canonical tenant backend consent, callback and disconnection. The full proposal remains active. Credential UI/redirect destination, browser acceptance, runtime refresh/secret use, live Google consent and the other resource/execution/approval boundaries remain pending. Existing Real hosts and user data were preserved.

## Implemented behavior

- `TenantCredentialOAuthService` resolves the actual owning Credential, requires current scoped read/manage, and binds the initiating human Account/session to its actual tenant User/Principal. Permissions precede stale witnesses and private proof preparation. Setup exposes only configured/Synthetic/host flags under read authority. Agent identities cannot initiate consent using a copied Principal or session.
- Start generates random state/correlation material, pins trusted shared-client ID/redirect/mode/host and the Credential logical/AuthEpoch witnesses, prepares protected PKCE/nonce proof, then atomically records the attempt/security/audit. Existing grants are unchanged until connection succeeds. Both stores now recheck the actual Credential revision/purpose/status/AuthEpoch when claiming before releasing private proof, closing a stale-preparation window even with a fresh security witness.
- `TenantGoogleOAuthProvider` uses shared `GoogleOAuth` settings only; legacy Gmail/Drive clients and unstamped legacy grants are not fallback. The private verifier/nonce use an AttemptId-bound, separate Data Protection purpose/application and `CredentialProtectionKeyRoot/credential-oauth`. Missing/tampered/wrong-attempt proof fails closed; the configured key ring can reopen an outstanding attempt after host restart.
- Real exchange uses fixed Google URLs, Authorization Code + S256 PKCE, offline consent, nonce verification through the existing Google signature/audience/verified-email helper, closed purpose-specific scopes, and Gmail/Drive profile email matching. Raw access/ID/refresh tokens and provider DTOs stay inside Infrastructure. Only normalized identity/scopes and a Credential-bound protected, client-stamped refresh grant cross the port. The dedicated HTTP client has no request/response loggers or retry/diagnostic body handlers, no redirects/cookies and a 20-second request timeout; bodies are capped at 64 KiB/depth 16. The attempt's remaining lifetime also cancels the complete exchange, including identity validation waits.
- Claim consumes private proof once before I/O. After I/O, original session/Account/membership, current scoped authority, trusted provider descriptor, deadline and Credential witnesses are fresh again before atomic commit. Logout, password rotation, suspended membership, grant revocation, disable, host disable, newer start, cancellation or expiry cannot save a prepared grant. Failed reconnect preserves the earlier grant. Caller cancellation marks the claimed attempt failed and propagates cancellation; deadline cancellation returns a safe failed outcome. Invalid provider data/body/identity parser exceptions are normalized without echoing secrets.
- Canonical authenticated cookie/CSRF setup/start/disconnect routes live under `/api/v2/tenants/{tenantId}/credentials/{credentialId}/oauth`. The separate public callback root is `/api/v2/integrations/tenant-google/oauth`. Its host-only HttpOnly Lax correlation cookie is restricted to that path and expires with the attempt. The Strict Account cookie may be absent after a Google redirect; the original stored session must remain live. A present different Account, missing/wrong proof, wrong callback mode, replay or superseded attempt is rejected. No legacy owner token fallback exists.
- Accepted callbacks delete the correlation cookie and redirect only to the fixed stored-Tenant/Credential destination with `connected`, `denied` or `failed`; request Host and caller return URLs do not choose it. Purpose routes enforce HTTPS/trusted-loopback development policy, no-store, no-referrer and restrictive CSP. Synthetic consent is a bounded provider fixture, not the completed product Credential UI. Its state/cookie flow requires no Google account, keys or network even with real-shaped settings present.
- Disconnect commits local grant removal and supersession first, then attempts bounded remote revocation using only the stamped shared client. `providerRevoked: false` truthfully preserves local disconnection. Runtime use remains separately unauthorized through the legacy sinks.
- `CredentialOAuthExpiryWorker` retires at most 100 expired attempts at startup and each minute using the registered clock. Its only successful diagnostic is a count; failure diagnostics contain a type name only. It has no copied user authority and cannot connect/disconnect a grant. Terminal-record retention/final schema consolidation remain pending. No new migration is needed for this successor; provider host state is inside the existing descriptor JSON.

## Executed workflows

The first runnable HTTP journey logged in, created Gmail/Drive Credentials, read safe setup, started consent with CSRF, checked the secure narrow cookie, then used an independent client with only that correlation cookie. Both purposes displayed Synthetic consent, connected, redirected to the fixed tenant destination, rejected replay, returned safe connected metadata, and disconnected. Network probes recorded zero attempts.

Additional HTTP cases rejected missing proof, a different authenticated Account, a Synthetic attempt sent to the Real callback, owner-capability substitution, missing CSRF, stale/superseded attempts, revoked original sessions, disabled Drive and invalid/oversized consent fields without echoing them. Cancel remained disconnected. A disposable SQLite host was stopped after start and recreated with its database/key root; the cookie-only callback then recovered the pending protected proof and connected. This verifies backend restart, not the missing Credential page or browser journey.

Both-store Application cases paused actual exchange and changed permissions, session, membership, Credential status, host state, supersession or logical time before release. All refused the grant, cleared/retired the claimed proof and produced no connect audit. Caller cancellation propagated without saving; a separate deadline case advanced logical time and observed completion while the provider gate was still unreleased. A denied actor with stale witnesses was rejected before private key creation. Raw claim cases changed Credential metadata and used fresh security revision, verifying no stale private proof was released.

The real adapter ran against offline HTTP responses with an internal test identity verifier. Tests checked exact client/redirect/code fields, PKCE challenge/verifier, nonce/audience handoff, closed scopes, fixed profile URL and bearer header, separately protected/client-stamped refresh grant, AttemptId/key-ring binding and revocation form body. They verified successful local disconnection after both successful and failed remote revocation. Wrong profile, broad mixed scopes, missing refresh token, oversized/error body, nonce rejection and malformed identity proof each failed a one-use reconnect while retaining the original grant, with no repeated token POST. These fixtures do not prove live Google signature/key fetch/consent or provider account behavior.

Actual worker execution on both stores started with an expired attempt, waited for its count diagnostic, then verified Expired outcome and cleared private proof with unchanged Credential value/generations, tenant security and audit. This uses logical time and a diagnostic publication barrier, not sleep-based timing.

During execution the gated authority cases exposed that `AccessDeniedException`/`SecurityConflictException` are independent of `AgentCoreException`; callback recovery now handles all three and marks failures terminal. Review also added claim-time actual Credential fencing, bounded malformed form handling, identity-parser exception normalization and the whole-exchange deadline. Each affected path was rerun after correction.
