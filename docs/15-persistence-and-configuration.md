# Persistence and Configuration

## Identity foundation schema and configuration

Typed tenant Session lifecycle mutations reuse existing Session/snapshot/entry rows and add no schema. Security CAS, Session revision, current human/session and safe audit commit together; deletion also removes direct Session assignments. The owning root remains retained and inaccessible after logical deletion. Conversation entries become content-redacted tombstones preserving IDs, sequence, opaque effect identity and source/Activation foreign keys; no referenced entry row is removed. Summary and pending context are cleared. This is not physical erasure of retained Run/Activation evidence or external bytes. [Both-store, race and SQLite reopen evidence](reports/tenant-session-lifecycle-verification-2026-10-17.md) leaves tenant runtime persistence, live coordination, automatic recovery and resource cleanup open.

Intermediate migration `20261016233720_TenantSessionOwnership` creates `TenantSessions` over the existing Session/snapshot rows. Composite restrictive foreign keys bind `(SessionId, AgentInstanceId)` to the actual Session, `(TenantId, AgentInstanceId, ExecutorPrincipalId)` to its SystemIdentity, and `(TenantId, CreatedByPrincipalId)` to a tenant User. Corresponding alternate keys and tenant/Instance indexes enforce these edges. CreatedAt uses UTC milliseconds. Global Account Principals retain nullable TenantId; the creator key is on TenantUsers. There is no adoption, backfill, second conversation store or global local-user profile creation. Session Instance identity is immutable. InMemory retains equivalent owning markers and shares the registered backing; returned Definitions are isolated snapshots. Creation, security CAS and audit commit together after current human/session, executor and source checks. [Schema/reopen and race evidence](reports/tenant-session-ownership-verification-2026-10-17.md) does not complete tenant runtime persistence or the final clean-schema consolidation.

Canonical Google connection checks add no table or migration. `TryCheckCredentialOAuthAsync` uses the existing security/Credential transaction or shared InMemory lock, verifies original human/session liveness, and compares security/logical/secret generations before applying a derived transition and audit. Successful checks leave authorization unchanged; optional protected refresh rotation increments only SecretRevision. Permanent rejection clears the protected payload, increments logical/secret/AuthEpoch and marks ReconnectRequired, superseding older consent work. A competing disconnect, disable, rotation, account/session revocation, cancellation or failed CAS cannot restore stale authorization. [Executed check evidence](reports/tenant-oauth-check-verification-2026-10-17.md).

`CredentialOAuthAttempts` is added by `20261016211213_TenantCredentialOAuthAttempts` in fresh disposable graphs. Composite restrictive foreign keys bind `(TenantId, CredentialId)` to the Credential root, `(TenantId, PrincipalId, AccountId)` to the human tenant User, and `(AuthenticationSessionId, AccountId)` to the original session. These last two parents gain alternate keys. Times use UTC milliseconds and attempt Revision is a concurrency token. A partial unique index permits one Pending/Claimed attempt per owned Credential; a deadline/outcome index supports bounded expiry. Begin caps unexpired active attempts at 128 per Tenant and supersedes any predecessor for that Credential. Claim clears the durable private proof and only returns it to its winning caller. Terminal failure/supersession/expiry also clear it. The provider now generates the private PKCE verifier and nonce and protects them through a separate Data Protection application/purpose bound to AttemptId, under `Persistence:CredentialProtectionKeyRoot/credential-oauth`. Preserve this key ring with the database; missing proof fails closed. `CredentialOAuthExpiryWorker` checks at startup and each minute with the registered clock, retiring at most 100 expired attempts per pass. It has no copied user/session authority and cannot grant or revoke a connection. Terminal-row retention/consolidation remains pending.

Email/Drive profile rows now carry the same nullable Tenant marker as the intermediate legacy split, with composite Credential-root foreign keys. Canonical writes always derive a non-null Tenant and canonical reads exclude null/foreign profile owners before counts/pages. Unique `(TenantId, GoogleSubject)` indexes separate external identities by Tenant and purpose; the old subject-only index now applies only to unowned null-Tenant rows. There is no automatic profile adoption/backfill. InMemory enforces equivalent identity uniqueness. Protected connection/disconnection and attempt outcome commit atomically with Credential/security revisions and audit; original Account/session/stamp/membership checks run inside that transaction/lock using the registered clock. [Store evidence](reports/tenant-oauth-store-verification-2026-10-17.md) is supplemented by [backend callback/provider/cleanup wiring evidence](reports/tenant-oauth-flow-verification-2026-10-17.md); UI, secret use and final schema consolidation remain open.

`AgentCredentialBindings.TenantId` is server-derived for canonical rows. Composite foreign keys `(TenantId, AgentInstanceId)` → SystemIdentity and `(TenantId, CredentialId)` → Credential owner prevent either cross-tenant edge. SystemIdentity's agent Tenant/Instance backing columns are required and have a composite alternate key; Credential owners expose their existing tenant/ID uniqueness as an alternate key. Instance/reference and Instance/Credential unique indexes remain. Canonical reads join both owners and actual protected rows, not just the Tenant column. Migration `20261016195121_TenantCredentialBindings` adds these constraints to fresh disposable graphs. No empty/zero owner defaults are supplied. Fresh migration/model parity and actual cross-tenant FK rejection are tested. This does not authorize applying an intermediate migration graph to user data or silently adopting old rows; final reset/consolidation remains required.

`TenantCredentials` owns an existing Credential ID with a restrictive Tenant foreign key, globally unique primary key, tenant/ID index and UTC-millisecond `CreatedAt`/nullable `DeletedAt`. Active ownership requires both an unretired root and the actual protected row. Retired roots remain exclusion markers after payload/profile deletion. The existing Credential/profile/binding tables remain the content owners; no shadow inventory or plaintext column is added. InMemory uses the same registered credential backing and Instance lock. Tenant writes commit value/root, security CAS and safe audit together, with logical/secret revision checks and current Account fencing. Exact credential grant retirement is part of deletion; bound deletion is refused.

The tenant Instance transaction additionally stores sparse settings, execution budgets, unattended model defaults and management policy in their existing parent JSON/columns with security CAS/audit. Exactly one change kind is accepted. Settings reconciliation participates in the same transaction; failed plans leave settings, parent/security revisions and audit untouched. Existing SQLite serialization provides the same independent snapshot boundary. No migration was added. [Settings evidence](reports/tenant-instance-settings-verification-2026-10-16.md).

Canonical Instance configuration uses existing Instance/persona revisions and Skill/resource/Automation rows, with no additional migration. Owned snapshot reads share one transaction/lock. Persona or exact-version changes commit with tenant security CAS, current Account status and audit; adoption rechecks the actual owned publication/status/metadata witness and initializes inherited Skill states from that stored payload. Observed Automation registration revisions/status changes commit in the same write boundary. Invalid persona/source/plan, cancellation or stale CAS leaves Instance/security/audit unchanged. The [configuration report](reports/tenant-agent-configuration-verification-2026-10-16.md) records both-store and SQLite reopen evidence; the final full schema consolidation below remains required.

Canonical Instance child changes use the existing Skill/resource state rows, parent revision and private content store; no migration or parallel storage was added. SQLite stages child writes within the tenant security/audit transaction, and InMemory commits under the shared security/Instance locks. Child witnesses and nested ownership are checked before mutation; mixed child operations are rejected except the atomic customize source-choice/local-copy pair. Immutable resource bindings verify actual stored bytes before commit. Deleting a local binding retains shared blobs; a failed CAS can retain a private unbound blob but cannot expose it by hash. Global Instance inventory/find/maintenance omit owned roots; public child read/write ports reject them. Trusted canonical helpers operate on the same records and retain SQLite reopen semantics. [Child evidence](reports/tenant-instance-children-verification-2026-10-16.md).

Instance child IAM reuses the existing Resource-type/ID assignment columns and indexes without a migration or generic resource registry. Canonical IDs combine the actual Instance GUID and existing child key; the same readable local Skill ID in two Instances is distinct. Both store ownership checks consult current local/source/manifest records. Removed inherited state can remain dormant for inheritance semantics without remaining an IAM target. Child deletion/adoption removes corresponding assignments under the same parent/security/audit commit; malformed, stale, foreign or raw writes retaining removed-target grants leave the graph unchanged. SQLite and InMemory serialize grant/delete races through the same security witness. Shipped-source resolution uses explicitly composed immutable builtin/approved-resource catalogs. [Scope evidence](reports/tenant-instance-child-iam-verification-2026-10-17.md).

InMemory passes cancellation through child-source validation and checks it before committing security state. These checks preserve Account-suspension fencing even when source reads occur after service preparation.

Store checks join all actual records, reject foreign/fabricated references and serialize grant/delete against the same security witness. Removal/publish/draft deletion/root deletion require retired grants to be removed inside the same transaction; SQLite reopen preserves this. Shared immutable content is retained. No migration or parallel child store was added. [Definition resource IAM evidence](reports/tenant-definition-resource-iam-verification-2026-10-17.md).

Tenant Agent identities require this actual backing resource; existing identity IDs, Principal, tenant and backing reference are immutable. InMemory retains the same roots and rejects backing deletion. Security aggregate validation rejects fabricated/foreign resource assignments for current member, role and registered-agent targets. Beyond these, the definition owner and owner-qualified Instance children described above, additional resource families remain unavailable to resource-scoped IAM until their ownership implementation exists.

`TenantAgentDefinitions` is the tenant-owned definition root, with an opaque canonical GUID-D string ID, restrictive Tenant FK and tenant/ID index. It remains present when a draft is consumed. Nullable `DeletedAt` (UTC milliseconds) permanently marks a retired root; active ownership queries and IAM assignments require it to be null, while global exclusion and ID collision checks include retired roots. The existing draft/publication/resource/evaluation tables remain the content owners. Canonical queries join the root for tenant ownership; global/unscoped authoring queries exclude owned roots and their children. Canonical mutations use explicit owned queries and the same rows, with tenant security CAS and audit. No second publication catalog or copies for global lookup are introduced. UTC root creation time uses the same SQLite millisecond conversion as security records.

Definition publication checks current required evidence and physical resource bytes, binds immutable publication resources, consumes draft/resources/evaluation records and updates security/audit in one transaction. Fork copies exact publication bindings into its new draft. Account status is rechecked under the same write boundary. Resource-scoped definition assignments are validated against this root inside security writes; merely passing a GUID shape is insufficient. Bootstrap cannot pre-seed resource identities/grants.

Canonical shipped-template forks retain nullable `AgentDefinitionDrafts.SourceDefinitionId` (max 64) with existing source kind/version. The target Definition ID is a new opaque GUID; it cannot serve as the original template identity. Ordinary New and owned-publication fork drafts have no external source ID. Source provenance/creation time are immutable on subsequent canonical saves. Initial resources use the existing draft resource table, actual immutable bytes and the same limits; no second template publication catalog is stored. Root/draft/initial bindings/security/audit commit together, and all content is checked before any owned graph is accepted. File-source reads/listing use the existing descriptor-relative filesystem with explicit no-link operations; current workspace link behavior remains unchanged.

Canonical draft/logical deletion uses the same tenant security CAS and current Account check. Logical deletion compares every draft revision and publication metadata revision, checks actual Instance/live Session/retained Run/Activation references, removes content/evidence rows and direct target grants, and marks the root deleted with one audit in the same transaction. Last-unpublished-draft deletion performs the same retirement; deleting a draft while another draft/publication exists retains the root and its grants. A conflict rolls back all changes. SQLite reference checks execute inside the transaction; InMemory composes the real shared Instance and session/run graph with the same lock order as admission. Retired roots survive reopen and cannot be rebound or re-created through global authoring.

Canonical child mutations use those same rows and owning root. Resource/scenario changes atomically advance draft and tenant security revisions with audit. Evaluation runs execute outside database locks and append evidence only after rechecking draft/scenario/fingerprint, tenant security CAS and current Account status. `AgentDefinitionDraftEvaluationResults.CommitRevision` is nullable for prior fixtures and assigned by the tenant transaction for canonical results. The `(DraftId, ScenarioId, CommitRevision)` index supports latest-evidence reads; commit order outranks timestamps. Snapshots select the latest result for each current scenario in the store; historical rows remain retained.

Immutable definition content remains private, content-addressed storage. Canonical HTTP cannot bind or read a supplied hash: attaching new data requires bytes, and metadata-only edits require an owned binding. Concurrent identical file puts use independent temporary paths, atomic no-overwrite placement and exact-byte verification of the winner; cleanup removes only the current writer's temporary file. A losing metadata CAS may leave a private unbound blob, never a readable cross-tenant binding. Draft/logical deletion removes owned bindings and evaluation rows transactionally; it never directly removes shared content blobs. Reference-aware blob GC and the final full lifecycle/retention consolidation remain pending.

Tenant security CAS, membership/role/invitation updates and audit commit together. The specialized tenant-agent transaction also commits the existing Instance and initial Skill state on create, or Instance lifecycle plus identity/Principal status on archive/restore. Failed revision/constraint writes leave no orphan Instance, identity or success audit. SQLite immediate transactions serialize mutations with Account suspension and last-active-Owner checks; stale operations do not append success audit. Authentication sessions store no bearer token or plaintext credential. Passwords use ASP.NET Identity's versioned PBKDF2 hasher; invitation tokens are random, hash-only at rest and purpose-bound. Credential rotation advances the Account security stamp and invalidates all earlier web sessions without copying permission snapshots into cookies.

Real uses the selected catalog verifier route and unchanged bounded platform budget. Synthetic registers `SyntheticTriggerCommandAuthorizer`, a typed deterministic fixture; optional `Synthetic:AutomationAuthorizationDecision` chooses its enum verdict for offline scenarios (default Allow). Automation mutations retain complete previews up to 131,072 characters and prepared argument JSON up to 65,536 UTF-8 bytes; generic/Drive bounds remain unchanged. Preparation also bounds exact verification JSON to 64,000 characters and refuses an oversized serialized preview before classification or approval persistence. No new table or schema migration is introduced. Reconnect restores the pending proposal and retained matching approval avoids another model call; changed target revision or action facts invalidate it. User cancellation, expiry and supersession remain existing Run transitions. Automation records, occurrence dedupe, policy and execution retain their existing owners.

## Three-layer context cutover

`AgentRunAdmission.TaskIntent` preserves admitted Automation instructions (with ID/revision) or a manual/immediate background objective. It participates in admission hashing and remains fixed across retries; raw trigger/event JSON never substitutes for it. Authored Automation projection fails explicitly if its frozen Automation task intent is absent or has another source.

Definitions and candidates use schema **2** and canonical `agentInstructions` / `AgentInstructions`. Instance overrides use the same editable field. Retired `systemInstructions` input is rejected, with no alias or dual writer. Published versions and optimistic revisions retain their identities during the explicit structural conversion; future publications remain immutable.

Normal startup does not convert populated data. `ContextCutover.ValidateAsync` inspects retained Definitions/drafts/Session snapshots, Instance overrides and Run configuration before current execution. Incompatible nonterminal checkpoints fail with an actionable maintenance error. The explicit offline `migrate-context` operation first creates a new SQLite backup using its backup API, then converts retained JSON in one transaction, validates the result and commits. It preserves Definition/draft/Instance versions, revisions, ownership and user data. Run configuration hashes and activation admission hashes use the same canonical constructors/algorithm as new admission. Existing draft evaluation fingerprints remain historical, so configuration changes require fresh evaluation before publication. Historical unsupported payloads cannot become live through a current-schema reader.

Admission rehashing uses the original Skill selection: pinned Always Skills plus accepted explicit user invocations when Composer admission succeeded. Later `skills.load` additions remain on the sealed Run but do not alter its admission identity. Replaying the original input after conversion returns the same sealed outcome; conversion does not execute tools.

Nonterminal Runs admitted under the retired schema must be drained/completed or explicitly cancelled using the prior application. Unknown/mixed checkpoints are never translated during normal execution. Completed Run checkpoint bytes remain inert historical audit evidence; original results and receipts are retained. No database, workspace, transcript, automation, memory, artifact or credential is automatically deleted.

New checkpoints have explicit context format **2**, Core contract **1**, interaction messages, typed Run phase/finalization/cleanup/protocol-repair state (including the optional `CompletionCorrectionAttempted` flag, default false for existing checkpoints), activation keys/counts, observation fences, pending call identities and redacted manifest. Existing enclosing checkpoint step/output/deadline/active-time fields remain authoritative. Core is rebuilt from the current compatible platform contract; Runtime comes from the frozen Run configuration plus current revocations. There is no prefix-count slicing or system-marker restoration. Back up the associated data roots with SQLite; downgrade requires restoring the matching application and backup.

`EntryCompletionTime` adds nullable `ConversationEntries.CompletedAtUtc` (UTC Unix milliseconds). The Session mailbox records assistant terminal time once (completed, failed or interrupted), independently of immutable `CreatedAtUtc`, and preserves it through checkpoints, save retries and history reads. Historical rows remain null; migration does not guess past completion times or change entry ordering. User and application-message publication times remain `CreatedAtUtc`.

## Workspace refinement storage and lifecycle

`Persistence:WorkspaceRoot` is an absolute normalized canonical root with `.canonical-layout` format `canonical-filesystem-1`. Its Instance home and Session working directories contain ordinary files, names, empty directories, modes and links. `.provisioned` remains beside working for one-time templates. Linked trusted ancestors/root substitutions fail closed. Relative configured roots are normalized once by DI.

Cwd is transient Session mailbox metadata shared by workspace and sandbox tools. It starts at `/home` or `/working` when home is disabled; it is never stored as a file. Cross-root copy streams current files and has ordinary partial-copy semantics. Session cleanup cancels IO, waits for its gate and confirmed container retirement, then purges only that Session. Instance cleanup requires committed deletion and its receipt; archive retains files.

A reopened snapshot loads the newest restore window, not every raw row. Older conversation rows stay in the store. A committed summary is the model-facing copy of the closed prefix; compaction does not delete or rewrite those rows. Conversation memory is agent-proposed and Core-admitted. Natural-language pattern matching is not the authority for durable memory writes. `MemoryPolicy` enables a scope; it does not admit every proposal. Envelope memory proposals carry no memory ids or owner ids, and the model does not write the store. Authorized continuity tools can inspect owned memory ids; memory.forget requires exact approval for the target item and cannot choose an owner. `MemoryAdmission` accepts a staged `MemoryProposal` from a model envelope, or a direct proposal from an application command, and then calls `StructuredMemoryService`. The completed assistant envelope stores the controller admission receipt apart from entry text and speech text. User-explicit failure stays visible after reload; inferred upsert/resolve outcomes stay silent, while rejected conversational deletion attempts remain visible. Store timestamps as UTC Unix milliseconds (`long`) with explicit EF conversions to DateTimeOffset, and GUIDs as canonical text. Do not depend on SQLite ordering arbitrary DateTimeOffset strings or rowversion support. Session.Revision is an application-managed optimistic concurrency token. ## Write ordering and recovery

One persistence write is in flight per Session Runtime. Capture immutable snapshots and serialize write dispatch, coalescing pending periodic checkpoints to the newest state. The mailbox still accepts interrupt/end events while writes execute. After a store write, persist completion returns through the mailbox with persist-token identity; only a still-pending token may apply. Advance durable revision only for that acknowledged snapshot, then start the next write. Apply subsequent dirty state to the next revision. Never let an old snapshot overwrite new spoken-until or terminal state. Checkpoints waiting behind an in-flight write collapse to the newest queued checkpoint; user-turn, pause, terminal, and other callback-bearing saves are not coalesced.

Durability boundaries: save on creation, accepted final user turn, response terminal, mode change (including queued `PendingMode` while the session remains attached), pause/disconnect and end. On pause/disconnect persist `PendingMode=null` even if a voice request was queued; Mode stays the last **applied** mode (Text if voice never started). During active generation checkpoint at most once per second, preserving only currently assembled text and conservative heard/received offsets. A 1-second streaming checkpoint **must not** rewrite every historical conversation row. Persistence identifies/upserts changed or currently streaming entries plus changed snapshot/session metadata. Immutable completed historical entries are not rewritten every checkpoint. Transactional SaveAsync, expectedRevision and optimistic-concurrency semantics are unchanged; Snapshot.Entries in the in-memory contract may still list the full session, but the Infrastructure writer must not issue no-op UPDATEs for unchanged completed rows. User turn generation waits for its save acknowledgement; final response completion waits for terminal save acknowledgement. Checkpoints cannot mark a still-streaming response completed. Temporary storage failure pauses new generation, emits recoverable SessionPersistenceUnavailable and retries local save after 1/2/5 seconds (maximum 3 retries); continued failure cancels active output, invalidates the attachment and pauses a non-ending session for explicit reconnect. An Ending session remains Ending until its terminal save succeeds; it cannot resume. Conflict is fatal for that runtime because it indicates a second writer or bug.

A crash may lose up to the last checkpoint interval of streaming text/progress, but not a user turn whose save succeeded. On startup/load, reconcile Attached→Paused and Streaming→Interrupted transactionally; set `PendingMode=null` so crash recovery does not auto-enter voice; keep the last recorded heard offset, never assume unacknowledged audio was heard. After attach, a trailing completed-user suffix with no later started assistant entry is one next user-turn; if an assistant entry for that suffix already exists (including Interrupted after recovery), do not start another. Ending recovers by completing the end transaction before attach; it cannot return to active. Provider streams, audio, timer generations and connection leases are never resumed.

## Shared durable execution and historical migrations

The current Session/Activation/AgentRun transaction owns accepted-input admission, frozen execution configuration, claims, retries, approvals, effect receipts and terminal outcomes. ## System credentials and protection storage

`Credentials` stores CredentialId, DisplayName, predefined Kind, Active/Disabled status, bounded non-secret metadata JSON, exact AllowedOrigins, protected payload, protection version, revision and timestamps. `AgentCredentialBindings` stores BindingId, AgentInstanceId, CredentialId, normalized Reference, revision and timestamps. Unique indexes enforce owner/reference and owner/credential. Owner deletion cascades grants; Credential deletion is restricted until all grants are removed. In-memory parity uses the owner lifecycle lock; SQLite mutations use transactions and revision concurrency checks.

The historical `20261007045013_SystemCredentials` change replaced `ApplicationConnections`; that migration is not in the executable chain. These tables are included in the current fresh-install baseline described above. Existing untracked or historical schemas are never adopted or upgraded implicitly, and this review performs no conversion or reset.

Legacy binding queries exclude actual tenant-owned Instances regardless of identity status. Legacy bind/unbind and bulk cleanup reject those owners under the shared Instance lock or SQLite transaction, before revising an Instance or removing bindings. Legacy Credential get/list/save/delete, OAuth rotation and binding creation additionally exclude/reject tenant-owned Credential IDs, including retired markers. Credential deletion still counts all references, including hidden bindings. Canonical management uses the specialized owner/security transaction described above; canonical binding configuration uses the owning transaction below, tenant OAuth correlation uses its original-human/session-bound attempt transaction, and runtime secret-use operations remain pending.

`Persistence:CredentialProtectionKeyRoot` defaults to `data/credential-protection-keys`. The local protector uses .NET Data Protection application name `AgentCore.Credentials` and purpose `AgentCore.SystemCredential`, version and CredentialId. The Unix key directory is owner-only. Loss of this key ring makes existing payloads unavailable with a bounded `credential_unavailable` error; plaintext never falls back into persistence. Preserve the database and key ring together, protect file access, and verify a restore. Compose stores keys at `/data/credential-protection-keys` in the same durable volume. This is local protection, not a hosted vault. P11C may replace the provider with an external vault/KMS/HSM without changing Credential semantics.

Display names are 1–120 characters. Metadata has at most 32 keys, 1–64 characters per trimmed case-insensitive unique key, 2048 characters per value, and 16 KiB total UTF-8 JSON. References normalize to lower case and contain 1–64 ASCII letters/digits/hyphens with an alphanumeric first character. Up to 32 exact HTTP(S) origins are accepted without paths, userinfo, query, fragment or wildcards. Protected input contains 1–65536 UTF-8 bytes and is never implicitly trimmed. Metadata is intentionally visible to agents; operators must keep protected material out of it.

Event bearer credentials remain Event-owned, shown once and stored as hashes. Host/provider keys stay in operator configuration. Neither is imported into this inventory.

The P9.5 nopCommerce Application Connection was a bounded proving slice and is retired by System Credentials. Historical P9.5/P9.6 freeze evidence remains unchanged; current behavior uses explicit credential grants, generic capabilities, and Agent-Instance-owned browser profiles.
